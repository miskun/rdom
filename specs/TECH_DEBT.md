# TECH_DEBT — open debt + accepted simplifications

Things rdom owes the codebase. Every item has a stable ID so it can be referenced from PRs, commit messages, and code comments without quoting the whole entry.

For the durable architectural divergences (web-platform departures shipped on purpose, intended to stay), see [`DIVERGENCES.md`](DIVERGENCES.md). This file is for the *temporary* simplifications and known follow-ups.

## Open

### Layout & cascade

- **`D-M2-2` — Static-position resolution simplified.** When `top: auto; bottom: auto` (or `left: auto; right: auto`), CSS uses the "hypothetical in-flow position" the element would have had. rdom simplifies to "containing block top-left edge." Real CSS resolution would require phase-1 to track hypothetical positions for absolute children — substantial layout work. Lift if real apps trip on it.
- **`D-M2-3` — Flat root-level z-sort instead of nested stacking contexts.** Correct for tooltip / dropdown / modal patterns; doesn't match CSS Appendix-E for nested stacking. Apps wanting truly local z-order can wrap in `position: relative; z-index: 0`.
- **`D-M2-4` — Negative z-index paints in flat sort order.** CSS 2.1 paints negative-z positioned elements *before* non-positioned content. rdom paints in pure `(z, doc_order)` ascending order — so a negative-z positioned element paints behind other *positioned* elements but ABOVE unpositioned content.
- **`LAYOUT-DISPLAY-NONE-STALE-RECT` — RESOLVED (2026-06-04).** A `display:none` element that had been laid out while *visible* kept its stale `ext.layout` because the in-flow filter dropped it without zeroing. Fixed in `layout_node`: after `layout_children`, `collapse_hidden_children` recursively zeroes `layout` + `content_layout` for every `display:none` child subtree (early-returns on already-zero subtrees, so steady-state hidden subtrees cost O(1)). Regression: `display_none_collapses_a_previously_visible_rect` (lay out visible → flip to none → re-layout → rect + descendant collapse to 0×0).
- **`PAINT-RELATIVE-ABSPOS-DOUBLE` — RESOLVED (2026-06-04).** The real cause was **stale `TuiExt.anonymous_blocks`**, not the relative position per se. When a block element has an element child, block layout wraps its inline run (own text) in an anonymous box and stores it on `anonymous_blocks`. When that child is later removed (e.g. the dropdown was dropped), the element becomes a pure-text leaf and takes the `flex::layout_children` pure-text-leaf carve-out — which set `inline_layout` but **never cleared `anonymous_blocks`** — so `paint_anonymous_blocks` kept painting the old inline run at its previous rect (the chip glyph echoing one slot over). The IFC carve-out had the same gap. Fixed by clearing `ext.anonymous_blocks` once at the top of `layout_children` (only the block-flow arm repopulates them), covering every dispatch path. NOT fixed by `LAYOUT-DISPLAY-NONE-STALE-RECT` (verified — zeroing the hidden rects left the double-paint). Regression: `relative_cell_glyph_paints_once_after_sibling_hidden_and_abspos_child_dropped` (App + `TestBackend`, incremental cascade) + verified end-to-end against rdom-virtualtable's old chip code.
- **`DRY-1` — partially RESOLVED (2026-06-04).** `is_in_flow(dom, id)` promoted from `block.rs` to `layout_pass::mod` and now the single source for the layout-side "skip out-of-flow children" filter (`flex::layout_children`, `layout_fragment_children`, the scroll-content walk). The paint (`recurse_children`) and hit-test (`descend_children_reverse`) filters carry extra concerns (z-list lift, inline-layout handling) and still inline their own checks — left for a follow-up that handles those carefully.
- **`D-M5N-8` — Positioned-pseudo content does NOT prefix-shift on left-edge viewport clip.** When a pseudo's layout rect starts at a negative viewport x, `layout_rect_to_grid` clips the rect's start to `clip.x` and `paint_text` writes the text's prefix at the clipped origin — the FRONT of the content shows where the back should have. Right-edge clip is correct (suffix dropped). Real CSS would shift the text rendering by the clipped-off cell count. Fix when prefix-shift becomes visible in real UI.
- **`M5-MIN-CONTENT-1` — RESOLVED (2026-05-25).** Implemented CSS Flexbox §4.5 `min-*: auto` semantics in the flex shrink pass: every flex item now floors at `min(content_size_suggestion, specified_size_suggestion)` along the main axis, with the spec exception that non-visible overflow drops the floor to 0. Implicit `min: None` follows strict CSS; explicit `min-*: auto` is more protective (always content size, regardless of specified cap) — see DIVERGENCES.md. The `flex-shrink: 0` declarations sprinkled across showcase demos are now redundant; cleanup is a follow-up. Strict CSS min-content (longest-word width with wrap) remains an approximation pinned to intrinsic natural size — see `M5-MIN-CONTENT-2` below if a real consumer needs the tighter floor.
- **`M5-MIN-CONTENT-2` — `min-content` width approximation.** rdom's intrinsic min-content for text uses the box's natural (unwrapped) width, not the CSS strict longest-word-after-wrap value. Difference matters only for narrow flex containers that hold long words — the floor is one cell-width higher than CSS strict. Refinement when a real consumer hits it.
- **`M5-MIN-AUTO-1` — `overflow: hidden → min-width: auto = 0` CSS exception not implemented.** Flex items with `overflow: hidden` still hold their intrinsic width — a tighter clip than CSS would produce. One extra branch in the resolver.
- **`M5-MARGIN-1` — RESOLVED (2026-05-26).** Full CSS 2.1 §8.3.1 vertical margin collapse implemented in `layout_pass/block.rs` (BFC-1 Phase 5): adjacent-sibling collapse (`max(positives) + min(negatives)`), parent-first-child / parent-last-child collapse with new-BFC + padding + border blockers (uses the cascaded `establishes_new_bfc` field from Phase 1), empty-block collapse-through, and full upward propagation of merged margins through `accumulate_outer_top_margin` / `accumulate_outer_bottom_margin` (chains the parent-first-child walk through every collapse-eligible descendant so the grandparent sees the merged margin at the parent's outer edge). Out-of-flow siblings preserve adjacency (filtered before run partitioning).
- **`BORDER-MODEL-1` — Border model refactor (in flight, `border-model` branch).** Single initiative replacing the heuristic stack around `border-collapse` with a layered, browser-faithful model:
  - **Layout** decides where boxes sit (collapse semantics only affect direct children of a declaring container, gap is sacred, no recursive transparent-intermediate propagation).
  - **Paint** decides which glyph + color paints at each cell (per-direction `(BorderStyle, Color, priority)`; conflict resolution per CSS Tables 3 §11.5).
  - **Cascade** changes: `border-collapse` becomes non-inheriting; `Border` carries a per-side `BorderStyle` enum (replaces bool); `hidden` is a kill-switch.

  Closes: `M5-COLLAPSE-1`, `M5.5b-CELL-OWNERSHIP-1`, `BFC1-CODE-COLLAPSE-INSETS-1`. Contract pinned in `DIVERGENCES.md` ("Layout" section). Milestone progress logged in `STATE.md`. The contract is the source of truth — if the implementation lags, that's a bug, not a divergence.
- **`M5-COLLAPSE-1` — RESOLVED by `BORDER-MODEL-1`.** Style conflict resolution now follows CSS Tables 3 §11.5 in full (hidden kill-switch → none losses → style ranking → child wins ancestor → later-DOM-order wins). `BorderStyle` enum in `rdom-style` carries the keyword set; cascade + paint enforce the algorithm per direction. Documented in `DIVERGENCES.md` under "Layout."
- **`M5-STICKY-1` — `position: sticky` v1 honors `top` and `left` only.** `right` / `bottom` insets and nested-scroller containing-block edge cases not implemented.
- **`CALC-PADMARG-1` — RESOLVED for padding/margin (2026-05-26).** `PaddingValue::{Cells, Calc}` and `MarginValue::{Auto, Cells, Calc}` now carry calc-with-percent through the full pipeline. Percent terms resolve at layout time against the containing-block width on all four sides (CSS 2.1 §8.3, §8.4). Layout: `compute_content_area_collapsed` resolves padding; `lay_out_block_child` / flex `resolve_margin` / positioning `axis_position_anchored` resolve margins. Parser: `padding-*` / `margin-*` accept `calc(<percent>%, <const>)`. Round-trip pinned by `padding_and_margin_calc_round_trip` in `property_dispatch.rs`; parse pinned by `calc_with_percent_in_padding_carries_through_as_padding_calc` (+ margin twin) in `crates/rdom-css/tests/integration/calc_parsing.rs`; layout pinned by `percent_calc_padding_resolves_at_layout_time` + `percent_calc_margin_left_offsets_block_child` in `crates/rdom-tui/tests/integration/calc_layout.rs`. **Two narrow follow-ups:**
  1. `BFC1-MARGIN-PERCENT-CHAIN-1` — `accumulate_outer_top/bottom_margin` walks the margin-collapse chain without a containing-block width in scope; calc-bearing margins resolve to 0 there (the percent term contributes 0). Visible only when a calc-percent margin participates in an upward-collapse chain. Real fix threads cb-width through the walkers.
  2. `CALC-GAP-1` — `gap` is still `u16` (no calc support). Smaller refactor; track separately.
- **`CHROME-SCROLL-GUTTER-DEFAULT-1` + `SUB-5` — RESOLVED (2026-05-26).** Implemented CSS `scrollbar-gutter` property end-to-end: enum `ScrollbarGutter::{Auto, Stable}` (default `Auto` matching CSS) added to `rdom-style`, parsed via `parse_scrollbar_gutter`, cascaded via `apply_scrollbar_gutter`, consumed by `layout_pass::reserve_scrollbar_gutter`. `Overflow::Scroll` axes always reserve. `Overflow::Auto` axes reserve only when `scrollbar-gutter: stable` is set (matches CSS `auto` default — scrollbar overlays the rightmost content column when it appears). `paint_pass::scrollbar::paint_vertical_scrollbar` / `paint_horizontal_scrollbar` take a `self_reserves_gutter` flag and shift the track position by 1 cell to overlay content when no gutter is reserved. Chrome workaround undone — `.main .source-disclosure { overflow: auto }` works correctly now without losing the closed-disclosure row.
- **`BORDER-PER-SIDE-LONGHAND-1` — RESOLVED (2026-05-26).** `Border` is now a struct `{ top, right, bottom, left: bool, corner_style: CornerStyle }` so any combination of sides is representable. Per-side longhand parsers `border-top` / `border-right` / `border-bottom` / `border-left` land in `property_dispatch.rs` and merge with the current `style.border` (so `border: solid; border-top: none` correctly clears just the top). `CornerStyle::{Square, Rounded}` carries the corner-glyph choice (only meaningful when all 4 sides are drawn). The legacy `border: top|bottom|left|right` shorthand keywords still parse as single-side borders via `parse_border`. The chrome's `.main .source-disclosure { border-top: solid }` and `.parse-and-render { border-bottom: solid }` declarations now actually render. Regression pinned by `chrome_layout_contract::source_disclosure_has_border_top` in `crates/rdom-showcase/tests/integration/chrome_layout_contract.rs`.
- **`BFC1-PERF-MARGIN-CHAIN-1` — `accumulate_outer_top_margin` / `_bottom_margin` walk descendants per child placement.** `crates/rdom-tui/src/render/layout_pass/block.rs::accumulate_outer_top_margin` and `accumulate_outer_bottom_margin` recurse into the collapse-eligible chain every time `lay_out_block_child` places a child. For a tree N deep with M-wide block lists at each level the same chain is walked at every depth — O(N²) in pathological cases. Memoize per node id within a layout pass (e.g. cache `Option<MarginAccumulator>` on `TuiExt`, invalidated at `layout_dom` start) or fold the chain walk into a single pre-order pass. Bench coverage in `crates/rdom-tui/benches/block_layout.rs` will reveal whether real shapes hit this; pay down when it does.
- **`BFC1-PERF-INLINE-FLOW-LOOKUP-1` — `inline_flow_for_text` is O(anon-boxes × lines × fragments) per call.** `crates/rdom-tui/src/render/inline/mod.rs::inline_flow_for_text` linearly scans every fragment in every anon box looking for one whose `text_node` matches. Today's anon-box Vecs are short, but this is called from every keystroke that moves the caret. For a `<p>` with 200 lines of text + a handful of `<code>` spans, each arrow-key press walks all 200 lines. Index `text_node → InlineFlow` lazily on the parent (HashMap built on first lookup, invalidated when the inline layout changes), or store the back-pointer on `TuiExt` of the text node's owner.

- **`BFC1-MARGIN-PERCENT-1` — RESOLVED via `CALC-PADMARG-1` (2026-05-26).** `margin-*: calc(<percent>%, <const>)` parses and resolves at layout time against the containing-block width. - **`BFC1-MARGIN-PERCENT-CHAIN-1` — Margin-collapse chain walkers don't resolve calc-percent margins.** `accumulate_outer_top_margin` / `accumulate_outer_bottom_margin` in `crates/rdom-tui/src/render/layout_pass/block.rs` walk parent-first-child collapse chains without a containing-block width in scope; `vertical_margin` is called with `cb_width = 0`, so calc-bearing margins contribute only their constant term to the chain. Visible only when a calc-percent margin participates in an upward-collapse chain (parent margin collapses with first-child's calc-percent margin). - **`CALC-GAP-1` — `gap` doesn't accept `calc()` with percent.** `Gap` is still `u16`. `gap: calc(2 * 3)` works (constant folds at parse time); `gap: calc(50% + 1)` is rejected. Small refactor — wrap `u16` in `GapValue::{Cells, Calc}` and resolve at layout time. Defer until a consumer hits the limit; flex/block consumers all use plain integer gaps today.
- **`SCROLLBAR-AUTO-TWO-PASS-1` — `Overflow::Auto` triggers a second layout pass when overflow is detected.** CSS Overflow 3 §3: `scrollbar-gutter: auto` behaves per the platform's scrollbar kind. Classic platforms (Windows, GTK, all native HTML form controls) consume space when the scrollbar is present; overlay platforms (modern macOS) don't. TUI is structurally classic — cells can't be overlay-composited — so rdom takes the classic path. `Auto` without `scrollbar-gutter: stable` lays out once without the gutter; if overflow is detected, `layout_pass::layout_node` reruns `layout_children` with the gutter forced (`reserve_scrollbar_gutter_forced`). Convergent in two passes (narrower viewport can only increase overflow). Cost: ~2× layout work for every `Auto` container that overflows on at least one axis. Acceptable today; revisit if benches surface it. Two narrow follow-ups: (1) the `height: auto` resolution and outer-height writeback in pass 1 isn't re-run in pass 2, so a parent whose height depends on content that wrapped differently in the narrower viewport stays at the pass-1 height (rare in TUI text — wraps are deliberate, not opportunistic — but a real edge case); (2) `record_scroll_content_size` reruns in pass 2 but its `scroll_y` carry-back assumes children's main-axis cursor accounted for the gutter on pass 2 (it does, via `parent_scroll` reading post-pass content_layout). File separate entries if a consumer hits either.
- **`FOCUS-THUMB-NEAREST-1` — the focus scrollbar-thumb cue colors every overflowing scroll ancestor, not just the one the keyboard scrolls.** `FOCUS-VOCAB-1` marks the focused scroll region with `:focus-within::scrollbar-thumb { color: accent }` (a layout-free cascade pseudo). But `:focus-within` matches the focused element AND every ancestor, so when two nested scroll containers both overflow at once, both thumbs colorize — while `runtime::scrollbar::handle_scroll_key` scrolls only the *nearest* scrollable ancestor. The cue (all) doesn't match the behavior (nearest). Accepted because (a) `::scrollbar-thumb` only paints when a scrollbar is actually shown, so only *overflowing* ancestors colorize — usually exactly one (the nearest content-bound one); and (b) the precise fix is layout-dependent ("is this a scroll container" needs post-layout overflow state), so it can't be a static pseudo — it'd be a post-layout pass marking the nearest scroll-container-of-focus with an attribute (`[data-rdom-scroll-focus]::scrollbar-thumb`), updated on focus + scroll change. Revisit with that marker if a real nested-scroller UI surfaces the mismatch. Documented in `DIVERGENCES.md` (focus affordances).
- **`M5.5b-CELL-OWNERSHIP-1` — RESOLVED by `BORDER-MODEL-1`.** The "child wins the shared cell" layout-side widening is preserved (`compute_content_area_collapsed` still expands content_layout to the outer rect for direct children of a collapse container with their own border). What changed: the model is now layered explicitly — layout positions borders such that they can share cells; paint composites per-direction (style, color, priority) and emits the winning glyph + color per CSS Tables 3 §11.5. The `collapse_parent_edge_insets` patch survives but uses a direct-child border check only (no transitive descent), so the "padding on a transparent intermediate eats the inset" class of bug is structurally impossible. Paint scrollport remains `compute_padding_box` (CSS Overflow 3 §3 padding-box) — that 2026-05-26 split stands.

Descendants that depend on the parent's content rect at layout time (the percent-resolution path is guarded by `nearest_block_ancestor_height_is_definite` so percent height isn't affected; sticky positioning + scroll content size DO read live `content_layout`). - **`FLEX-BLOCK-MAIN-INTRINSIC-1` — A `display: Block` flex item with no explicit width oversizes itself in a flex row.** Observed building the `permission_dialog` showcase demo: `<input type=radio>` (UA `display: Block`, no `width`, intrinsic content width = 4 cells from the `( ) ` / `(•) ` pseudo content) ended up `w=20` in a 50-cell-wide `<label>` whose `display: flex; flex-direction: row` made the input a flex item. The sibling `<span>` correctly took its intrinsic 10 cells. Workaround: replace per-item `margin-bottom` with `gap` on the container (which IS counted correctly). - **`FLEX-ITEM-NEGATIVE-MARGIN-CROSS-AXIS-1` — Negative cross-axis margins on a stretched flex item don't extend the item past the parent's content area.** Observed building the `permission_dialog` showcase demo: setting `margin-right: -1` on a flex item inside a `display: flex; flex-direction: column` container (default `align-items: stretch`) had no visual effect — the item stayed pinned to the parent's content-area edge instead of extending 1 cell beyond it. Per CSS Box Model §8.3.1 a negative margin should cause the box to overflow its containing block; per CSS Flexbox §9.4 `align-items: stretch` resolves an item's cross-axis size from the line's cross size minus the item's cross-axis margins, so negative margins should *expand* the item past the line edge. Suspect site is `crates/rdom-tui/src/render/layout_pass/flex.rs`'s cross-axis sizing — the stretch path likely clamps to the line's cross size without applying the negative-margin adjustment. Worth a focused test on `align-items: stretch` + negative margin before fixing; the spec is subtle around how negative cross-axis margins compose with `justify-self` / `align-self` overrides.

### Cascade misses

- **`D-M1-3` — RESOLVED (2026-05-26).** The original entry mis-described the gap: the substrate already had `TextDecoration::LineThrough` → `Modifier::CROSSED_OUT` in the cascade (`apply_text_decoration`), and `sgr::emit_sgr_transition` emitted SGR-9 for that bit. The real leak was in the paint helpers: `style_from_computed` and `glyph_style_from_computed` masked the modifier bitset with `BOLD | ITALIC | UNDERLINED` only — `CROSSED_OUT` was dropped between cascade and cell write. Fixed by adding `CROSSED_OUT` to both masks; regression pinned by `text_decoration_line_through_paints_crossed_out_modifier_on_cells` in `crates/rdom-tui/src/render/paint_pass/tests.rs`.
- **`D-M1-4` — RESOLVED (M4 era, doc-only retirement 2026-05-26).** `crates/rdom-tui/src/cssom/observer.rs::InlineStyleObserver` is installed by `App::build` (via `cssom::install_default_observers`) and watches `Mutation::AttributeChanged { name: "style", … }`. ### Animations

- **`D-M3-2` — Timing function parser is named-keyword only.** `cubic-bezier(a, b, c, d)` and `steps(n, position)` are not parsed. The bezier evaluator inside `TimingFunction::ease()` is parameterized — only the parser needs the follow-up.
- **`D-M3-3` — Pseudo-element transitions deferred.** The cascade produces `computed_before` / `computed_after` / `computed_backdrop` / `computed_selection` on `TuiExt`, but `diff_and_register` only inspects the main `computed` slot. Apps can't transition pseudo-element styles.
- **`D-M3-5` — Microtask integration runs three drains per tick.** Could batch into one. Profile-driven if it becomes hot.
- **`D-M3-6` — Discrete properties under `transition: all` are not midpoint-toggled.** CSS L1 says discrete properties (display, position, content, …) under `transition: all` switch at midpoint; rdom's diff loop only registers animations for properties in the animatable enum. Apps explicitly transitioning a discrete property via `transition-property: display` get a warning.

### Paint pipeline

- **`OPACITY-1` — Group rendering for proper CSS opacity composition.** The current 0.1.0 implementation composites per-paint-op (cell-level), which works correctly for the common cases (element with bg + opacity, z-stacked translucent elements). Two divergence pockets remain:
  1. **Pseudo + own bg + opacity** — pseudo elements carry `bg` in the glyph style (they have no upstream `fill_bg`). Under `opacity < 1.0`, the compose pipeline blends pseudo's bg against the cell's already-blended element bg — a small color shift.
  2. **No opacity multiplication / no CSS group rendering** — a parent with `opacity: 0.5` containing a child with `opacity: 0.5` renders the child at 0.5, not the CSS-correct 0.25.

  Proper fix is subtree group rendering: each element with `opacity < 1.0` renders its entire subtree into a temporary `Buffer` at full opacity, then composites that buffer at the element's opacity. Eliminates both pockets. Defer until a real consumer hits a case the approximation produces wrong output for.

- **`TREE-BFC-PSEUDO-1` — `::before` / `::after` paint incorrectly on mixed-content blocks.** A block with a direct text run AND a block child (e.g. `<li>Label<ul>…</ul></li>`, or any nested-list markup) routes its inline run through BOTH `paint_inline_content` (Path 4, which prepends `::before`) AND `paint_anonymous_blocks` (which repaints the same run without the pseudo offset). The two paints land at different x and the tail duplicates (`"> Cluster"` → `"Clusterer"`). Surfaced building the ARIA tree: the disclosure chevron was moved out of `::before` into the guide paint pass to dodge it, and the `ul > li::before` list-marker is suppressed for `[role=treeitem]`. Root fix: anonymous-block layout must reserve the `::before` width as the first fragment of the first anon block (layout change) and Path 4 must not repaint own text when `anonymous_blocks` is non-empty. NB: the *height* half of this mixed-content bug (next sibling overlapped the block's children because the block-stacking cursor used the pre-layout `intrinsic_size` estimate, which counts element children only) WAS fixed in the same change — `block.rs` now advances the cursor by the child's actual laid-out height.

### Substrate gaps

- **`SUB-2` — RESOLVED (2026-05-26).** Closed by BFC-1 Phase 3: text-only containers (`<p>only text</p>`) now route through the **pure-text-leaf** carve-out in `flex::layout_children` — same `compute_inline_layout` packer the IFC path uses, just structurally reached without requiring an inline element. Mixed text-plus-block content folds inline runs into anonymous block boxes per CSS 2.1 §9.2.1.1. The `is_ifc_block` predicate keeps its narrow "at least one inline ELEMENT child" definition because that's the path that wants to walk an entire descendant subtree as one inline flow; the carve-out is the simpler structural shortcut.
- **`SUB-3` — UA `<style>` rule placed at end of defaults array.** The rule for `style { display: none }` was added at the end to avoid breaking source-order-indexed tests. Cosmetic. Pay down when the UA stylesheet is reorganized.
- **`SUB-4` — `i16` ceiling on `Length::Cells`.** Positioning offsets max out at ±32k cells. Probably forever-fine; flag if anyone reaches for a virtualized scroll surface beyond the 16-bit range.
- **`SUB-5` — RESOLVED (2026-05-26).** Closed by `CHROME-SCROLL-GUTTER-DEFAULT-1`. The CSS `scrollbar-gutter` property is now implemented with `Auto` as the default — gutter cells are no longer reserved unconditionally for `Overflow::Auto`. Authors that want stable layout (no reflow when a scrollbar appears) opt in via `scrollbar-gutter: stable`. The `both-edges` keyword variant remains unimplemented; file a follow-up if a consumer needs it.
- **`CSS-BG-SHORTHAND-1` — `background` shorthand isn't parsed; only `background-color` longhand works.** `rdom-style::property_dispatch` registers `background-color` but no `background` entry, so `background: red` and `background: transparent !important` silently no-op (the parser rejects the declaration; the cascade never sees it). Authors building real-world consumer code hit this whenever they reach for the common shorthand idiom. Surfaced building the `permission_dialog` showcase demo's `:focus-within` highlight — the demo had to switch to `background-color: …` longhand to override the UA's `:focus` bg. Fix: add a `background` parser entry that accepts the color-only subset (CSS 2.1 §14.2.1 minus image/repeat/attachment/position, which rdom doesn't paint anyway) and dispatches to the same `bg` slot.
- **`SCROLL-CROSS-AXIS-1` — flex scroll only translates the MAIN axis; the cross axis isn't scrollable.** `layout_pass::flex::layout_flex_children` subtracts `parent_scroll(direction)` from the child's *main*-axis cursor only (`flex.rs:537-605`); the cross-axis scroll offset (`scroll_x` for a `Column` container, `scroll_y` for a `Row` container) is never applied to the child's cross position, and cross-axis sizing stretches children to the container, so there's nothing to scroll cross-wise at the container level anyway. **Consequence:** a vertically-stacked container — notably `<table>`, which is a `Column` flex — can't be its *own* horizontal scroll container. **Browser-faithful workaround (and the idiomatic web pattern):** wrap it in a *same-axis* `Row`-flex `overflow-x` container (the TUI analogue of `<div style="overflow-x:auto"><table>…`); the existing main-axis scroll handles it and header+body translate together — pinned by `table_in_a_horizontal_scroll_wrapper_scrolls_header_and_body_together` in `layout_pass/tests.rs`. Real fix is two parts: (1) apply cross-axis scroll in flex positioning, (2) let cross-size exceed the container under non-visible overflow so there's content to scroll. Deferred — the wrapper covers the real use case (wide tables) exactly as the web does.
- **`TABLE-COLSPAN-1` — `colspan` / `rowspan` unimplemented.** `table::size_columns` measures one cell per column index; a spanning cell would need a real table-layout algorithm. **Not needed by the virtualized-table consumer:** spacer rows for virtual scrolling can use per-column empty cells (each contributes 0 content width, so column alignment is undisturbed) or a spacer outside the table. Web-standard, so adding it later is no divergence — it's simply absent. File a sized entry if a consumer needs genuine spanning cells.
- **`TABLE-TFC-1` — rdom tables are a flex masquerade, not a real Table Formatting Context. Roadmap-level overhaul.** `<table>` is `display: block`, `<tr>` is a flex Row, cells are flex items; there is NO table-specific layout. Column alignment comes from a pre-pass (`size_columns`) — see `TABLE-COLSYNC-1` below for the de-conflation fix that makes it spec-faithful for the common case. The **full** browser table model remains future work: real `Display::{Table,TableRow,TableCell,TableColumn,…}` with anonymous-table-box fixup (wrap a stray `<td>`, synthesize missing `<tr>`/`<table>`), the complete CSS 2.2 §17.5.2 *automatic* algorithm (per-column min-content/max-content with table-width redistribution), `colspan`/`rowspan` width spreading (`TABLE-COLSPAN-1`), **percentage** column widths, and honoring **CSS-rule** (not just inline/`<col>`) cell widths. This is a large, self-contained milestone (new display variants + a dedicated layout algorithm + UA-rule + border-collapse re-integration + cell/row-height model) justified only when a consumer genuinely needs `display:table` on arbitrary elements or spanning cells. Until then, the de-conflation fix (`TABLE-COLSYNC-1`) delivers predictable, resizable columns for the real consumers; the structural gaps above are the deliberate divergence (documented in `DIVERGENCES.md`). Grumpy-architect note: building the TFC now would be gold-plating — it imports per-frame layout cost, border-collapse re-integration, and a half-built display model for fidelity nobody is asking for.
- **`TABLE-COLSYNC-1` — RESOLVED in code (2026-06-04, releasing as 0.3.6).** Was: `size_columns` conflated author width (input) with computed width (output). De-conflation fix (web-faithful, bounded). `size_columns` writes its measured column widths back onto every cell's **`inline_style.width`** (author space) and stamps `data-rdom-colsync` to force a re-cascade — so an author's explicit width can't survive (the next run overwrites it, and the pass can't tell its own prior write from author intent). That's the root cause behind dead `Column.width`, the colsync dirty dance, the `::after` sort-glyph clip, and "resize needs substrate." **Fix:** the pass (a) **respects explicit widths** — a column whose cells carry an author `inline_style.width` (or, later, a `<col width>`) uses it as the column width; only un-specified columns are content-sized; (b) writes the *used* per-column width to a **layout-side field** on the cell (`TuiExt`), read by flex as a main-size override — **never** to `inline_style`; (c) drops the `data-rdom-colsync` stamp (widths are read by full layout each frame, not by the incremental cascade, so no dirty signal is needed). This obsoletes `TABLE-COLSYNC-DIRTY-1`. **Divergence (documented):** explicit column widths are honored via inline `style="width"` or `<col width>`, **not** via a CSS rule (`td { width }`) — that needs the post-cascade in-layout computation of the full TFC (`TABLE-TFC-1`).
- **`CSS-INHERIT-KEYWORD-1` — `inherit` / `initial` / `unset` CSS-wide keywords aren't parsed.** The `Value::Inherit` and `Value::Initial` enum variants exist in `rdom-style::value` and are honored by the cascade's apply pass (each property's resolver branches on `Value::Inherit => parent_value`), but **no parser path produces them from CSS source** — `parse_color`/`parse_length`/etc. all reject the bare `inherit` ident as an unknown value, so the whole declaration silently drops before reaching the cascade. Authors who write the textbook `color: inherit` to opt out of a UA rule get nothing. Surfaced building the `permission_dialog` demo's Dismiss button — wanted `color: inherit` to drop the UA's `button { fg: accent }`, ended up with `color: reset` (rdom-specific keyword that maps to `Color::Reset`/terminal default). Fix: thread a CSS-wide keyword check ahead of per-property parsing so any property that supports `Value<T>` accepts `inherit` / `initial` (and ideally `unset` = `inherit` for inherited properties, `initial` otherwise). Touches every property's `Value::Specified` wrap path — small per-site, but it's many sites.

Milestone D.

### Substrate honesty (0.3.5 — surfaced by `rdom-virtualtable`, the virtualized-table consumer)

- **`TABLE-COLSYNC-DIRTY-1` — RESOLVED (2026-06-03).** (Was: `size_columns` width writes weren't re-cascaded.) `table::size_columns` writes each cell's width straight to `ext.inline_style.width`, which fires **no** mutation — so the runtime's *incremental* cascade (`draw_if_dirty` → `cascade_subtrees_all` over dirtied roots only; layout is full) never re-cascades those cells. It bit the `<thead>` cells specifically: a consumer that rebuilt only the `<tbody>` (a virtualized table swapping its row window) dirtied the body subtree but not the headers, so the headers kept a **stale computed width** while full layout read it — the column shifted, fixed only by an unrelated later mutation (e.g. navigating right toggled `data-active-col` on the headers). The downstream crate worked around it by stamping a revision attribute on the table itself. Fix: `size_columns` now stamps a column-width signature (`data-rdom-colsync`) on the `<table>` **only when the widths change**; the resulting `AttributeChanged` marks the table a dirty root, so the whole table subtree (headers included) re-cascades and every cell picks up its new width. One attribute, fired only on an actual change. Consumers drop their own dirty hack. Tests: `size_columns_dirties_the_table_only_when_widths_change` / `size_columns_stamps_a_stable_colsync_signature` in `runtime/builtins/table/tests.rs`.

### Events

- **`ITERM2-MOUSE-MOTION-1` — iTerm2 unreliably honors `?1003h` (any-motion mouse tracking).** Symptom: rdom-tui sends `EnableMouseCapture` (which includes `?1003h`) at `enter_tui_mode` and crossterm reports it written. iTerm2 sometimes accepts it and `Moved` events flow normally; sometimes silently drops the mode and only `Down` / `Up` / `Drag` events arrive (clicks and button-held drag work, free motion doesn't). The unreliability appears at app launch and re-appears after every unfocus/refocus cycle. User-visible: CSS `:hover` styles don't react to the cursor moving over elements until a click "wakes" the terminal up. **What we tried (none worked):** per-byte mode writes, pre-reset (`?1003l`→`?1003h`), focus-cycle toggle (`?1004l`→`?1004h`), periodic re-arm in the event loop (broke iTerm2 worse — repeated DEC mode sends made the terminal stop accepting mouse capture entirely), `?1003l`→`?1003h` toggle in the event loop (same), re-arming on `FocusGained`. **Root cause:** iTerm2 commits to motion tracking only after receiving a real user mouse event (Down/Drag/Up); no output sequence we can send replicates that signal. The protocol is one-directional — apps cannot inject mouse events back to the terminal. **Verified absent on:** Alacritty, Kitty, Ghostty, WezTerm (per codex's analysis; not personally tested). **Workaround for end users:** click anywhere in the terminal once after launch and again after refocus. Hover then works. **Don't try to fix again with output writes** — the empirical curve through this rabbit hole shows every output-side "fix" was either no-op or actively harmful. The next genuine improvement requires either iTerm2 fixing its `?1003h` handling, or a protocol-level addition for app→terminal input injection. Document the workaround in user-facing docs when those are written.
- **`SHOWCASE-EVT-1` — Event handlers cannot mutate the App's stylesheet stack.** Listeners registered via `dom.add_event_listener` receive an `EventCtx` with mutable access to the `Dom` but NOT the `App`. They can mutate the tree freely (`append_child`, `clear_children`, `set_attribute`) but cannot call `App::push_stylesheet` / `App::remove_stylesheet` because the App owns the cascade pipeline and event dispatch happens inside its outer loop. The showcase works around this by pre-pushing every demo's stylesheet at startup and relying on each demo's class-scoped selectors (`.flex-row-demo`, `.hover-demo`, etc.) for isolation — an unenforced-in-substrate convention pinned by a registry-level test in `rdom-showcase`. The workaround scales linearly: at N demos, every cascade pass walks N× the rules per element regardless of which demo is mounted. **Pay down with a substrate hook** — either (a) lifecycle observers the App installs that can mutate sheets in response to mutation records, or (b) a deferred-queue API on `EventCtx` for "App-level intents" the dispatch loop drains after the current event completes. Option (b) is the smaller change; option (a) is the more general one and aligns with how M5's implicit-event work needs to thread through the App anyway. **Defer to M5 or M7** — M5 already touches the App / observer plumbing for `EVT-DETACH-1`; do it then.
