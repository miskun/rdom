# DIVERGENCES — where rdom departs from the web platform

The rdom default rule is: **track the web platform.** WHATWG DOM, CSS Working Group specs, and UI Events are the reference. If a behavior is not listed here, it should match the web platform within the supported subset.

This document collects every deliberate departure in the shipped crates (current line: 0.5.x, heading to 0.6.0 under [`CSS-COMPLETE-2026-10.md`](CSS-COMPLETE-2026-10.md)). Departures fall into three groups:

1. **TUI medium constraints** — fixed by the fact that we render to a character grid.
2. **Simplifications** — places where rdom keeps a smaller model than the web platform.
3. **Not yet shipped** — web features rdom still omits, each named with the program item that will ship it.

Roadmap for what's coming next: see [`DESIGN.md`](DESIGN.md#roadmap).

---

## 1. TUI medium constraints

These are intrinsic to terminals. They will not change.

- **Integer cells only.** No subpixel positioning, no fractional widths, no anti-aliasing. Coordinates are `u16` cells.
- **A scrollbar is one cell, whatever `scrollbar-width` says.** No cell is narrower, so `thin` (CSS Scrollbars 1 §3) keeps the one-cell bar and its gutter and draws it lighter: no track glyph, the thumb in the track's light line (`│` / `─`) instead of the heavy one (`┃` / `━`). `none` hides the bar and reserves no gutter; the box still scrolls by wheel, keys and script (C8-SCROLLBAR). `scrollbar-color` fills the track's cells with the track color and draws the thumb glyph in the thumb color on it.
- **A fractional length rounds onto the grid.** Cells are integers, so a `<length>` with a fraction — written as a unitless number (`width: 2.5`, `padding: 0.5`), computed by a unit or a math function (`2.5ch`, `calc(50% / 3)`) — rounds onto the grid, half to even, as CSS Values 4 §10.9 rounds a computed value to the precision the medium supports. CSS reads a unitless non-zero length as invalid; rdom reads every unitless number as cells, the fraction included, so `2.5` and `calc(2.5)` are the same length (C4G-NUMBER-RANGE — until then a literal fraction was rejected while `calc(2.5)` was taken).
- **Alignment free space is shared in whole cells.** Where a browser hands out fractional pixels, rdom deals whole cells deterministically, in flex layout and in block layout alike: the free space `flex-grow` shares (and the overflow `flex-shrink` takes) rolls, so the shares sum to the whole space — two growing items over 31 cells get 15 + 16; the free space `auto` margins share, and the free cross space `align-content: normal` (`stretch`) gives a multi-line container's lines, is an equal share each with a remainder cell to each of the first margins / lines; `justify-content` / `align-content: center` round the leading space down (toward main-start, an odd cell after the items), and `space-between` / `space-around` / `space-evenly` place each item (line) at its rolling position rounded up, so the remainder cells go to the first spaces; `align-items` / `align-self: center` round the leading cross space down; in block layout `justify-self: center` (a block-level or absolutely positioned box in its containing block) and `align-content: center` (a block container's content), and an absolutely positioned box's `align-self: center`, round the leading space down too, as do `auto` margins centering an absolutely positioned box; `text-align: center` rounds a line's leading space down, and `justify` gives each justification opportunity the same share of a line's free cells, the remainder one each to the first opportunities (C9-TEXT-ALIGN); in grid layout an item's `justify-self` / `align-self: center` and two `auto` margins round its leading space down, and `justify-content` / `align-content` distribute the free space around the tracks as flex distributes it around its items (the same code).
- **Grid tracks are whole cells.** The track sizing algorithm (CSS Grid 2 §11) hands out its free space as the alignment entry above does: space shared equally — the extra space a spanning item needs (§11.5.1), the free space that maximizes the tracks (§11.6) and stretches the `auto` ones (§11.8) — is an equal share each with a remainder cell to each of the first tracks that can take one; an `fr` track's share (§11.7) and a spanning item's share of flexible tracks by flex factor (§11.5 step 4) roll like `flex-grow`'s, so the shares sum to the whole space — `2 1fr 2fr` in 13 cells is 2 + 3 + 8. Rounding each step may leave a grid sized to its content a cell larger than the exact algorithm would.
- **A transition moves geometry a whole cell at a time** (C12-ANIMATABLE). A running transition's value is the element's computed value, so layout reads it each frame (CSS Transitions 1 §3, Web Animations 1 §5.4.5). A length that layout reads in whole cells — `width`, `height`, `padding`, `margin`, the insets, `gap`, `flex-basis`, grid tracks, `min-*` / `max-*` — interpolates exactly and rounds to the nearest cell, ties to even, as a `calc()` result does: `height: 0 → 5` is 2 rows at 50 % (2.5) and 4 at 70 % (3.5). A length and a percentage mix as `calc(cells + percent%)`, which layout resolves and rounds once. A length kept fractional for paint (`border-radius`, `box-shadow` offsets, `letter-spacing`) interpolates its fraction, and its used value rounds or floors where it always does.
- **Monospaced advance.** Variable-width fonts are out of scope.
- **Letter and word spacing are whole blank cells** (C9G-LETTER-SPACING; CSS Text 3 §9.1, §9.2). `letter-spacing` and `word-spacing` take `normal | <length>` in cells — a bare number, `ch`, a viewport or line-height unit; a pixel or font-relative length is invalid, as for every length that is geometry (DESIGN "Pixel lengths select, cells measure"), so a browser stylesheet's `letter-spacing: .1em` is dropped with a warning, and Text 4's percentage is not taken. The used spacing floors to whole cells (`1.9` is one, `.5ch` none — as a fractional `line-height` floors) and is never negative: glyphs cannot be drawn closer than a cell apart, where a browser lets them overlap. The spacing is blank cells after a unit — every grapheme and space for `letter-spacing`, each word separator for `word-spacing` — none after the last unit on a line (§9.2), after a tab (it reaches its tab stop), after an atomic inline, or inside a cursive script (Arabic, Syriac, N'Ko, Mandaic, Mongolian, Phags-pa); the caret, hit-testing and selection treat a unit and its spacing as one, so a click on the spacing after a letter is on that letter.
- **No images, no SVG, no pixel painting.** `<canvas>` is a cell-painting escape hatch via `RenderContext`, not a pixel-painting surface.
- **Length units.** Sizing accepts cells (unitless numbers — an integer, or a fraction, which is the length `calc()` of it is: `1.5` and `calc(1.5)` alike, in every cell-length property; C4G-NUMBER-RANGE), rdom's flex `fr` unit, `%` (resolves at layout time against the basis each property's spec names), `ch` (exactly one column on a monospaced grid) and `lh` / `rlh` (the element's and the root's used `line-height` in whole rows, absolute at computed-value time; in `line-height` itself `lh` is the parent's, and on the root `rlh` the initial one row — C2-LH, C9-LINE-HEIGHT; a registered custom property's `lh`, computed before `line-height` is, is one row); a fraction rounds onto the grid where the value becomes a length. The absolute units (`px`, `cm`, `mm`, `Q`, `in`, `pt`, `pc`) and the font-relative units (`em`, `rem`, `ex`, `cap`, `ic`) depend on a pixel or a font size the terminal grid does not have: a declaration using them is dropped as an invalid value, with a warning — except in the properties whose length decorates rather than lays out (next-but-one entry). Decided in Phase 2 of CSS-COMPLETE (C2): no terminal mapping (say `1em` = one cell) is offered — `CSS-COVERAGE.md` classes these units N/A, and a guessed pixel or font size would make browser CSS lay out at an arbitrary scale rather than fail visibly. The viewport units are percentages of the terminal (next entry).
- **`attr()` reads attribute values literally under `type()`.** CSS Values 5 §8.7.1 substitutes `var()` / `attr()` found inside an attribute's value before parsing it against the `type(<syntax>)`; rdom parses the value as written, so such a value fails the syntax and takes the fallback. The syntaxes `type()` takes are the ones `@property` checks (§2 "Registered custom properties"). Attributes have no namespace: `attr(|x)` is `attr(x)`, and `attr(ns|x)` never finds one. A `:root` custom property's `attr()` reads the tree's root when it is an element (`Dom::with_root_tag`); the default root is a document fragment, which has no attributes, so there it takes the fallback. The `<url>` taint rule (§8.7.2) has nothing to guard — rdom has no `url()`.
- **The viewport is the terminal.** `vw` / `vh` are 1% of its columns / rows, `vi` / `vb` the same in horizontal-tb (every box lays out as horizontal-tb, below), `vmin` / `vmax` of the smaller / larger. A terminal has no retractable UI, so the small (`sv*`), large (`lv*`) and dynamic (`dv*`) viewports all equal it. As on the web they are absolute at computed-value time: the cascade resolves them against the document's viewport, which every cascade form reads (`CascadeExt::set_viewport`; `layout_dom(area)` records its area; the `App` sets its terminal's size each frame and cascades the whole tree again when it changes), and a percentage beside them stays for layout. A headless document's viewport is 0 × 0 until set or laid out.
- **A border is one cell wide; its width picks a glyph weight.** Every border side occupies exactly one cell, whatever its `border-width` (a cell is the smallest unit, and a two-cell border would read as two lines): the width selects the glyph set instead. `thin` and `medium` (the initial value) draw the light set (`─│┌┐└┘`), `thick` the heavy set (`━┃┏┓┗┛`); a pixel length is light below `thick`'s 5px and heavy from it, a cell length light below two cells and heavy from them (larger widths clamp to heavy); `0` removes the side — no cell, no glyph (CSS Backgrounds 3 §4.3), while its computed `border-style` stays what was declared. Sides of different weights meet in the mixed junction glyphs (`┍┑┿╽`); `double` keeps its own glyphs at any width, and Unicode has no heavy rounded corner, so a heavy rounded corner is square. Because a width never becomes cells, `<line-width>` also takes the absolute units (`px`, `cm`, `mm`, `Q`, `in`, `pt`, `pc`, at CSS's fixed ratios to the pixel) and `em` / `rem` at the CSS initial font size, 16px — `border: 1px solid red` is the most common border on the web — kept in CSS pixels (`PaintLength::Px`), so they cannot change a layout. A math function whose lengths are all such units takes the same path (`calc(2px)`, `max(1px, 0.1em)`, `calc(2 * 3px)`; CSS's own typing, so a number is only a factor), folded to pixels when parsed — CSSOM reads it back as `2px`, not `calc(2px)` — while one mixing pixels with cells, `ch`, viewport units or a percentage is invalid: a pixel and a cell have no common measure (DESIGN "Pixel lengths select, cells measure"; C4G-PX-CALC).
- **A text field has no UA border** (C11G-FORM-BORDER). Every engine draws a text `<input>` / `<textarea>` with a native inset border of a pixel or two (HTML's rendering section leaves the widget's appearance to the user agent); in a terminal a border is a whole cell on each side, so a one-row `<input>` would be three rows tall and its 22 columns 24. rdom's UA field is `padding: 0 1` on a `Field` background instead. So `input:user-invalid { border-color: red }` paints nothing — the field has no border style. Mark a state with the field's colours (`input:user-invalid { background-color: red; color: white }`), or give the field a border and pay its rows (`input { border: solid } input:user-invalid { border-color: red }`) — the rdom-tui README's "Form states" section has both, as a test.
- **An outline is a whole-cell ring** (C12-OUTLINE; CSS UI 4 §5). The ring is the row and column of cells just outside the border box, `outline-offset` cells farther out (a pixel offset is one cell its way, DESIGN "Pixel lengths select, cells measure"; a negative one draws inside the box, over its content); `outline-width` only selects the glyph weight, as `border-width` does — light below `thick` / 5px, heavy from it, none at zero — since a ring cannot be thinner or thicker than a cell. The styles draw from the border glyph set (`ridge` / `groove` / `inset` / `outset` as a single line), and `auto`, the UA focus-ring look a browser leaves to the platform, is a light ring with rounded corners in the accent color when `outline-color` is `auto`. A ring cell replaces what is under it, a border junction included: it does not weld with the borders it crosses. As CSS 2.1 Appendix E step 10 puts it, a context's outlines are drawn after everything else it paints, its positioned descendants included. An inline box is ringed on each line it has a fragment on, one rectangle per line around the cells its text, generated content and atoms take there (§5.1 allows one non-rectangular outline or one per fragment; whole-cell rectangles keep each ring a box-drawing ring) (C12G-OUTLINE-INLINE).
- **A border corner takes one side's color.** Where two sides of a box meet, the browser splits the corner between them along the line from the outer to the inner corner, so each side colors part of it (CSS Backgrounds 3 §4.4) and the wider side the larger part. A cell holds one glyph in one color, so rdom gives the corner cell whole to the dominant side: the wider (heavier) side, then the heavier style (CSS Tables 3 §11.5's ranking, `double` above `solid`), and between equals the horizontal side — `border-color: red blue` draws all four corners red, so the top and bottom read as whole lines. Junctions between different elements' borders resolve by §11.5: the wider border, then the style, then the more nested and earlier element. The glyph joins every direction's line where Unicode has one: a double line meeting a single one draws the mixed glyphs (`border-style: double solid` has `╒` / `╕` / `╘` / `╛` corners, a collapsed junction `╤` / `╧`; `╓╖╙╜╞╟╡╢╥╨╪╫` likewise). Unicode has no glyph where a heavy line meets a double one, nor where one axis is double on one side and single on the other; there the dominant side's set draws the whole cell.
- **A rounded corner is one arc glyph.** A non-zero `border-radius` (CSS Backgrounds 3 §5) on a corner draws `╭` / `╮` / `╰` / `╯` there, whatever the radius — a cell cannot show a larger curve — and a corner with either radius zero is square, as specified; elliptical (`/`) and percentage radii parse and only their zeroness counts (a percentage against the border box's width or height). The background is not clipped to the curve: the corner cell is one cell, and takes the background with the rest of the border box. Unicode has arcs only in the light set, so a corner whose sides are heavy (`thick`) or `double` is square; a corner shared with another element's border (a junction) is square too, as there are no rounded T-junctions.
- **A box shadow is a shade of whole cells.** `box-shadow` (CSS Backgrounds 3 §6.1) paints each shadow as cells in its color: an outer shadow is the border box moved by the offsets and grown by the spread, drawn outside the border box only and under the background; an `inset` one is the padding box less itself moved by the offsets and shrunk by the spread, drawn above the background and below the border and content; the first shadow is on top. Offsets and spread are whole cells — cell lengths rounded onto the grid, a pixel or `em` length one cell in its direction (`0 1px 3px` is a one-row shade under the box) — and the blur radius has no effect: a cell cannot be blurred, and a guessed pixel size would scale web shadows arbitrarily. An opaque shadow covers what lies beneath it; a translucent one composites over it like a translucent background (CSS Color 4 §4.2), which gives the classic darkened-cells terminal shadow. A shadow with zero offsets and spread is hidden by its own box, so a blur-only glow draws nothing.
- **Color.** `Color::Rgb` emits truecolor SGR sequences unconditionally; there is no `COLORTERM` runtime autodetection. A separate 256-color fallback exists as an explicit code path.
- **UA stylesheet glyphs assume BMP box-drawing support** (U+25xx, U+250x, U+256x). Terminals without these blocks are out of scope.
- **No bidirectional reordering.** `direction: rtl` works (C5-WRITING): the inline-start edge is the right one — lines start there, an over-constrained block or positioned box keeps its right margin / inset, a flex row runs right to left, the vertical scrollbar moves to the left, a scroll container scrolls from its right edge (`scrollLeft` 0 there, negative to the left). But rdom never reorders characters or inline boxes: the Unicode Bidirectional Algorithm and `unicode-bidi` are out of scope, because terminals differ — some reorder right-to-left scripts themselves, others print cells as given — so a line keeps its logical order left to right (what a browser shows for left-to-right text in an `rtl` paragraph; right-to-left script prints in logical order unless the terminal reorders it). `dir=auto` and `<bdi>` do take the direction of their first strong character (HTML §3.2.6.4, C11-LINK-LANG; how rdom classifies a strong character is in §2).
- **Every box lays out as `horizontal-tb`.** `writing-mode` parses, inherits and computes all five values, but a glyph cannot be rotated in a cell, so the vertical and sideways modes lay out horizontally — and the logical properties map as in `horizontal-tb` (block = top / bottom).
- **Synchronized output (DEC 2026 BSU/ESU) is always emitted** unless the `no-synchronized-output` feature flag is set.
- **CSS with no meaning on a character grid.** The *N/A* rows of [`CSS-COVERAGE.md`](CSS-COVERAGE.md). rdom rejects them like any unsupported CSS — the declaration, rule or at-rule is dropped with a warning — and will not implement them:
  - *Fonts* — the terminal owns the font: one monospaced face at one size. `font-family`, `font-size`, `font-stretch`, `font-size-adjust`, `font-optical-sizing`, `font-kerning`, `font-feature-settings`, `font-variation-settings`, `font-language-override`, `font-synthesis*`, `font-palette`, `font-variant*`; `@font-face`, `@font-feature-values`, `@font-palette-values`. (`font-weight` / `font-style` map onto SGR bold / italic, §2; `font-family`, `font-size`, `font-stretch` / `font-width`, `font-variant` in CSS 2.1's `normal | small-caps` form and the `font` shorthand parse, cascade and serialize, and draw nothing — C9-FONT; the other font properties are not parsed.)
  - *Images* — there are no pixels to draw them into. `url()`, `<image>`, gradients, `image-set()`, `<resolution>` (except as `background` / `background-image` values: below); `background-clip: text` (a cell cannot show a background through a glyph's shape; the declaration is dropped); `background-blend-mode` (parsed and kept, inert: a cell's one background layer has nothing to blend with — C15-BLEND), `border-image*`, `list-style-image`, `mask*` / `mask-border*` (parsed by their grammars and kept as text, drawing nothing — and, unlike CSS Masking 1 §6.1, a `mask-image` makes no stacking context; C15-CLIP-PATH), `shape-outside` / `shape-margin` / `shape-image-threshold`, `object-fit` / `object-position`, `image-rendering` / `image-orientation` / `image-resolution`.
  - *Sub-cell geometry* — a cell is the smallest addressable unit, and a glyph cannot be offset, scaled or rotated inside it. Absolute and font-relative length units (above); `text-shadow`; `text-emphasis*`; `initial-letter`; `hanging-punctuation`; `text-decoration-thickness` / `text-underline-offset` / `text-underline-position` / `text-decoration-skip-ink` (parsed, cascaded and kept for the CSSOM — they change nothing drawn, C9-DECORATION) and `text-decoration-skip` (not parsed); `dominant-baseline` / `alignment-baseline` / `baseline-shift` / `baseline-source` (one baseline per row); `display: ruby*`; vertical glyph orientation (`text-orientation`, `text-combine-upright`); the `transform` functions other than the translations, the `rotate` and `scale` properties and `transform-origin` (parsed, cascaded, serialized and animated, drawing nothing — any of them other than `none` still makes a transformable box a stacking context and a containing block, CSS Transforms 1 §2; C15-TRANSLATE); `zoom`; `filter: blur()` and `url()` (parsed and kept, drawing nothing; `drop-shadow()` draws as a whole-cell shade, C15-FILTER); `box-shadow` blur (its spread is whole cells, above).
  - *3D* — a grid has no depth. `transform-style`, `perspective`, `perspective-origin`, `backface-visibility`. (The 3D transform functions — `translate3d()`'s and `translateZ()`'s z offset, `rotate3d()`, `perspective()`, … — and `translate`'s z component parse and are inert, above.)
  - *Print and paged media* — a terminal is one continuous screen. `@page` and the page properties; fragmentation (`break-*`, `page-break-*`, `orphans`, `widows`, `box-decoration-break`); `string-set`, `bookmark-*`, `running()`, `content()`, `leader()`, `target-counter()`; `print-color-adjust`.
  - *Platform features a terminal app lacks* — speech (`speak`, `voice-*`, `pause*`, `rest*`, `cue*`): no aural output. `:visited`, `:local-link`, `:target`, `:target-within`, `::target-text`: no navigation history or URL fragments (`:visited` parses and never matches — every link is unvisited — so `a:link, a:visited` keeps its `:link` half). `:autofill`, `:fullscreen`, `:picture-in-picture`, the media-playback pseudo-classes, `:current` / `:past` / `:future`, `::cue`, `::view-transition*`, `::spelling-error` / `::grammar-error`: no autofill, fullscreen, media, timed text, view transitions or spellchecker. `env()` and `forced-color-adjust`: display hardware and modes a terminal does not report. `@namespace` and namespace selectors, `::part()` / `::slotted()`, `:defined` / `:state()` / `:host*`: no XML namespaces, Shadow DOM or custom elements (§2 DOM API shape). `::file-selector-button`: `<input type=file>` is not rendered. `input-security`: masking is control behavior here, not styling. `display: run-in`: implemented by no browser. `clip`: superseded by `clip-path`. `@charset`: sources are Rust `&str`, already UTF-8.

## 2. Simplifications from the web platform

### Layout

- **`row-gap` spaces a block container's block children.** CSS Box Alignment 3 §8 gives gaps to flex, grid and multi-column containers; rdom also puts a block container's `row-gap` between its adjacent in-flow block-level children (anonymous line boxes of inline content get none), on top of their collapsed margins — a terminal layout convenience kept from before the block formatting context landed. `column-gap` does nothing there.
- **The table formatting context is laid out in whole cells** (C13-TFC; CSS 2.1 §17, CSS Tables 3). A line between columns or rows is a whole cell or none: in the separated model `border-spacing` cells (no percentages, C4-SPACING), in the collapsing model one cell wherever any box on the line — the table, a row group, row, column (group) or cell — has a border there (`hidden` included, as under every collapse container below); the conflict on it is paint's (CSS Tables 3 §11.5). Every width and height a distribution hands out is whole cells, by the rolling floor flex and grid use (§1). Four departures: a cell spanning several columns spreads what they lack by how far each can grow (else by their max-content widths, else equally) and its percentage over their columns without one — CSS Tables 3's refinements by column type are not made; a caption's vertical margins collapse with nothing; an anonymous cell's block-level content (a block child of a row or of a table's stray run) stacks without margins; and table parts inside an inline box get no anonymous `inline-table` (§17.2.1 rule 3's inline case) — like any block-level box inside an inline box, they follow its packing ("Anonymous block boxes", above), while in a block container they get their anonymous `table`. A cell's `vertical-align` moves its content by whole rows: `middle` takes the upper of two middle rows when the free rows are odd (C13-TABLE-PROPS). A table's grid stops at 65 535 columns (C13G-SPAN-COST): HTML caps each `colspan` / `span` at 1000 but not their sum, and no terminal cell offset reaches past `u16::MAX` — a cell reaching past the cap is cut at it, one starting past it has no box — and the column model `||` and `:nth-col()` match stops there too (`rdom_core::table::MAX_COLUMNS`, C14G-CORE-GAPS): such a cell is in no column, a `<col>` past the cap represents none. HTML's UA `border-spacing: 2px` is not a whole cell, so a `<table>`'s cells touch (the initial 0), and its cells keep rdom's one-cell inline padding where a browser's is 1px — the cells' text stands two blank cells apart and rows touch, as a 2px gap does at terminal scale (kept by C13G-TABLE-UA; the rest of HTML §15.3.8's table rules apply as written).
- **`border-collapse` does not inherit, and outside a table it collapses a flex or block container's direct children.** In a table (`display: table` / `inline-table`) it is CSS's: the table formatting context collapses every cell, row, row group, column and column group border on its grid, however deep the cells sit under rows and row groups (CSS 2.1 §17.6.2, C13-TFC). Three divergence axes from CSS:
  1. *Scope.* CSS restricts `border-collapse: collapse` to table boxes; rdom honors it on any flex or block container too. Terminal UIs lean on shared-border rendering for non-table chrome. A grid container's items keep their own borders: grid gutters are the way to space them.
  2. *Inheritance.* CSS makes `border-collapse` inheritable. rdom makes it non-inheriting. A container that wants its children to participate must declare `border-collapse: collapse` itself — no spooky action across subtrees — and a table nested in a collapsed table's cell is separated unless it declares collapse too. The reset means demo / consumer subtrees never inherit a chrome's collapse decision implicitly.
  3. *Scope of effect in a non-table container.* Within a flex or block collapse container, the overlap-share affects only the container's **direct children**. The "transparent intermediate" recursive propagation present in earlier rdom builds is gone — to share borders with a more deeply nested element, every container in the chain declares collapse explicitly. A table is the exception named above: its grid is one collapse context.
- **A subgrid's items align their baselines among themselves.** CSS Grid 2 §9 has the items of a subgrid share baseline groups with the parent's items in the same row; rdom aligns a subgrid's `baseline` items within the subgrid only, and they add no baseline shim to the parent's rows (C7-SUBGRID). A subgrid itself is stretched on the axes it subgrids, so it never baseline-aligns there. On its other axis rdom keeps it out of its parent's baseline groups too: its baseline would need its size, which takes the tracks its parent has not laid out yet (C7G-MEMO-PURITY).
- **Grid re-resolution detects aspect-ratio transfers only.** CSS Grid 2 §11.1 steps 3–4 size the columns again when the rows changed an item's min-content contribution to them. rdom measures column contributions with no height input, so in a terminal only an item whose aspect ratio transfers a height the rows made definite into a width can change one, and that is what it checks (C7-GRID-RERESOLVE). One case it does not detect: a `flex-flow: column wrap` item, whose min-content width depends on a definite height (its lines wrap at it), keeps the contribution measured before the rows (C7G-MINOR).
- **The 2×2 outcome grid for `gap` × `border-collapse`** is the canonical reference for what authors get:

  | `gap` on parent | `border-collapse` on parent | Outcome |
  |-----------------|------------------------------|---------|
  | `0`             | `separate` (default)         | Adjacent children, each owns its own border (`┐┌`). |
  | `>0`            | `separate`                   | Visible gap between bordered children. |
  | `0`             | `collapse`                   | Direct children overlap by 1 cell at shared edges; paint emits junction glyphs (`┬┴├┤┼`). |
  | `>0`            | `collapse`                   | Visible gap. `collapse` is a no-op because there is nothing adjacent to share — `gap` always wins where the two would conflict. |

- **`border-style: hidden` is honored as CSS Tables 3 §11.5's kill-switch on any rdom collapse subtree, not only tables.** Wherever `hidden` appears in a border conflict, that direction is suppressed regardless of any other contributor. Same divergence axis as the scope extension above — rdom adopts the table conflict-resolution algorithm wholesale and applies it to the non-table cases the substrate enables.
- **Border-style support is the full CSS keyword set, with terminal-faithful degradation:** `none`, `hidden`, `solid`, and `double` render with distinct glyphs (`│─┌┐└┘` / `║═╔╗╚╝`); `dashed` and `dotted` draw Unicode's dash glyphs on their straight runs — `dashed` the double dash (`╌╎`, heavy `╍╏`), `dotted` the finer triple dash (`┄┆`, heavy `┅┇`) — while their corners and junctions, which have no dashed form in Unicode, take the solid glyphs (C4G-EDGE-TESTS). `ridge`, `outset`, `groove`, `inset` parse and rank correctly in conflict resolution but render as `solid` (matching CSS's "render as best you can on this medium" principle — the data model is faithful even where the glyphs aren't yet distinguishable).
- **Vertical margins collapse in block flow per CSS 2.1 §8.3.1** (`render/layout_pass/block/margin_collapse.rs`): adjacent in-flow siblings; a block and its first / last in-flow child when no padding, border or line box (inline content, an own-line `::before` / `::after`) separates them; empty collapse-through blocks; any number of levels up. Resolution is largest positive plus most negative. As on the web, nothing collapses horizontally, between flex items or inline-level boxes, or across an element that establishes an independent formatting context (flex container, flex item, inline-block, non-visible `overflow`, absolute / fixed position, the root element, and the initial containing block, through which the document root's children's margins never escape — among themselves they collapse, as `<body>`'s children's do; C13-ROOT-BLOCK). Clearance separates margins (CSS 2.1 §9.5.2): a cleared box's margin collapses with neither its siblings' nor — when it is the first in-flow child and a float ahead of it in the same parent is on a side it clears — its parent's (C8G-CLEARANCE-COLLAPSE). The gap: whether a first child has clearance is decided from the floats ahead of it in its parent only; a float from earlier in the formatting context that reaches below the parent's top does not stop the parent's top margin collapsing with the child's.
- **Percentage height resolves against a flex item's size.** Per CSS Flexbox §9.8 a flex item in a flex container of definite size has a definite post-flexing main size and, stretched, a definite cross size, so `height: <pct>%` on its content resolves against it — rdom treats every item of an element flex container (whose own height chains up to the container's) that way, on either axis, and an `<n>fr` (`Size::Flex`) height likewise. Block-flow `auto` heights are indefinite exactly as CSS 2.1 §10.5 requires. Gate: `nearest_block_ancestor_height_is_definite` in `crates/rdom-tui/src/render/layout_pass/block/height.rs`.
- **`aspect-ratio` rounds onto the cell grid** (half-to-even) and applies on the flex cross axis, from a definite main size, and to a flex base size from a definite cross size (CSS Flexbox §9.2 step 3.B, C6G-FLEX-SPEC); a grid item's `auto` width follows it from a definite height — declared, a percentage of its area, or stretched — and contributes so to its columns (CSS Sizing 4 §5.1, CSS Grid 2 §11.1 steps 3–4, C7-GRID-RERESOLVE), its `auto` height from its width under `normal` (§6.2); a block-level box in block flow takes its `auto` width from a definite height (rather than the stretch fit) and its `auto` height from its width, floored at its content unless it scrolls or sets `min-height` (§5.1, C14-ASPECT-BLOCK). The full `auto || <ratio>` grammar is parsed; nothing in rdom has a natural aspect ratio, so `auto && <ratio>` uses the ratio — on the content box, as the spec says for that form — and a degenerate ratio (a zero term) behaves as `auto`. Cells are not square (a terminal cell is about twice as tall as wide), so `aspect-ratio: 1` is square in cells, not on screen.
- **Anonymous block boxes (CSS 2.1 §9.2.1.1), not anonymous inline boxes.** Mixed inline + block children inside a block-flow container produce **anonymous BLOCK boxes** wrapping each inline run (text + `display: inline` + atomic `display: inline-block`). Each anon box establishes its own IFC. This matches CSS for block containers; what rdom does NOT yet generate is anonymous *inline* boxes for the `<span>foo <span>bar</span> baz</span>` text-around-inline-around-text shape inside an existing IFC (inline-ancestor-breaking). Texts inside one inline element render as a single fragment; nested inline-ancestor-breaking is deferred.
- **White space is processed per CSS Text 3 §4.1 with three simplifications** (C9-WHITE-SPACE). Each text is processed and wrapped by its own `white-space-collapse` / `text-wrap-mode` (they apply to text), but a soft wrap opportunity takes the `text-wrap-mode` of the text before it — the white space's own for an opportunity after white space — where §5.1 reads the nearest common ancestor of the two sides; they differ only where `nowrap` text starts or ends right at a letter boundary. The segment break transformation, UA-defined in Text 3 §4.1.3 and Text 4, removes a collapsible line feed next to a zero-width space or between two East Asian Wide / Fullwidth / Halfwidth characters neither of which is Hangul (so Chinese and Japanese broken across source lines join without a space), and makes every other one a space. Control characters other than tab, line feed and carriage return are not rendered, where §4 asks for a visible glyph. `white-space-trim` (Text 4 §4.2) is not parsed, so `white-space` takes no `discard-*` component.
- **Line breaking is a UAX #14 subset, without dictionaries** (C9-BREAKING; CSS Text 3 §5). Soft wrap opportunities are white space, the sides of ideographic characters (CJK ideographs, kana, Hangul syllables, fullwidth letters and any other two-cell grapheme), after a hyphen (unless a digit follows), a dash, a zero-width space, a soft hyphen (under `hyphens: manual` / `auto`) and `<wbr>`; none around glue (no-break spaces, the word joiner), before closing punctuation, infix separators or exclamation marks (`。` `、` `）` `.` `,` `!`), nor after opening punctuation; between two letters or digits only under `word-break: break-all` or `line-break: anywhere`. Characters of classes BK / NL (U+000B, U+000C, U+0085, U+2028, U+2029) force a break. rdom has no `lang`, so `line-break`'s rules for "Chinese or Japanese" (§5.3) apply where the characters on both sides are CJK, and `strict` differs from `normal` only by the spec's one listed rule (no break before `〜` `゠`); `auto` is `normal`. Southeast Asian scripts, which need a dictionary, do not break between words, and `hyphens: auto` is `manual`: rdom hyphenates only at soft hyphens. A word that ends at a soft hyphen reserves the hyphen's cell when it is placed, so a line may wrap one word earlier than a browser's where the hyphen would not have been shown. `overflow-wrap: normal` does not relax `keep-all` when a line has no other opportunity (§5.5's "may"). A caret at the boundary of two lines broken with no space between (between ideographs, after a soft hyphen) sits at the end of the first.
- **`text-transform` with four UA choices** (C9-TEXT-TRANSFORM; CSS Text 3 §2.1). `capitalize` starts a word at a letter or digit not preceded by a letter, a digit or a word-internal apostrophe — `don't` is one word, `well-known` two (as in Gecko and Blink), `3rd` keeps its `r`. Unicode's Final_Sigma context for `lowercase` is read within a text node (a `Σ` at the end of one, followed by a letter in the next element, still lowers to `ς`). `full-width` maps ASCII and its signs, a preserved space (U+3000) and the halfwidth katakana one to one — a halfwidth voiced mark (`ﾞ` `ﾟ`) becomes a spacing `゛` `゜`, not composed with the kana before it. `math-auto` (MathML Core §4.2) applies to any element whose text node is one character: rdom has no MathML. The transform is rendering only: the caret, selection and copy work in the source text, as §2.1 requires ("must not affect the content of a plain text copy & paste operation") and Gecko does; Blink and WebKit copy the transformed text (crbug.com/325231).
- **`text-indent` skips anonymous flex and grid items** (C9-TEXT-INDENT; CSS Text 3 §8.1). The first formatted line of a block container, of the anonymous block box holding its first inline content, and — with `each-line` — each line after a forced break are indented (`hanging` inverting which), in whole cells, a percentage of the block's content width; an intrinsic size counts the indent, a percentage there against 0 (CSS Sizing 3 §5.2.1, cyclic). The text of a flex or grid container is an anonymous item whose first line §8.1 would indent when it is the container's first child; rdom packs those items without the indent.
- **Justification is whole cells at a small set of opportunities** (C9-TEXT-ALIGN; CSS Text 3 §6.4). `text-justify: auto` expands word separators (spaces and no-break spaces) and the gaps beside a two-cell character (CJK); `inter-word` the separators only; `inter-character` every gap between two typographic character units, spaces included. The added cells are spaces painted after their unit — so a selection highlights them with it — and nothing is compressed. A line holding a preserved tab is not justified (§6.1 lets a UA treat such text as having no opportunities, so tab stops keep lining up), and a line with no opportunity is start-aligned. `text-align` is CSS Text 3's shorthand of `text-align-all` and `text-align-last` — engines treat it as a longhand — so a `text-align` declared after `text-align-last` resets it to `auto`, as the spec says.
- **`text-wrap-style` choices** (C9-TEXT-WRAP; CSS Text 4 "Selecting How to Wrap"). `balance` evens out each group of lines between forced breaks of two to six lines (Chromium's limit; the spec allows treating `balance` as `auto` past ten): the narrowest width cap on the group's lines that keeps its greedy line count, so the line count never changes; the lines keep their alignment in the full line box. `pretty` and `avoid-short-last-line` apply one rule: when the block's last line holds one word (no space) and the line before it more than one, that line's last word moves down, if the line count does not change — words are space-separated, so CJK text is left as it is. `stable` is `auto`: rdom's line breaking is greedy and never looks at later content. A paragraph with a float in it or a line beside a float keeps its greedy breaks (a replay would place the floats again).
- **`line-height` is whole rows** (C9-LINE-HEIGHT; CSS Inline 3 §5.1, CSS 2.1 §10.8.1). The font is one row tall, so `normal` and `1` are one row, a number is that many rows and a percentage that share of a row, and a fractional used line height — number, percentage or length — floors to whole rows (`1.5`, `150%` and `1.9ch` are one row, `2.5` two; C9G-LINE-HEIGHT-FLOOR): leading under a row cannot be drawn, and a terminal row already carries the font's line gap, so a reset's `line-height: 1.5` keeps one row per line, where rounding would double-space the page; a line height below one row is one — the glyph's own row, where a browser lets the lines overlap. Half-leading puts `floor((L − 1) / 2)` leading rows above the glyph row and the rest below, so an odd leading's extra row goes below. A click on a leading row places the caret in that line's text, but targets the block, not an inline element (whose box is its glyph row).
- **`vertical-align` is whole rows, and one property** (C9-VERTICAL-ALIGN; CSS 2.1 §10.8.1). `sub` and `super` move the box one row — the parent's subscript and superscript positions on a grid — and the line grows to hold it, as a browser's does; a length moves it that many rows, a percentage that share of its line height, rounded ties to even. `middle` puts the box's middle row (the upper of two) on the parent's baseline row: half the parent's x-height above its baseline is inside that row. `text-top` / `text-bottom` align the box with the parent's glyph row, its content area. An inline element's box is its line-height box, an inline block's its margin box; a `top` / `bottom` box taller than the rest of its line grows the line downward / upward (where CSS leaves the placement to minimize the height, Blink's choice). CSS Inline 3 makes `vertical-align` a shorthand of `alignment-baseline`, `baseline-shift` and `baseline-source`; rdom keeps CSS 2.1's single property and parses none of the three (§1: one baseline per row). Table cells are not aligned by it yet (C13-TABLE-PROPS, §3).
- **Text decorations are the terminal's SGR attributes** (C9-DECORATION; CSS Text Decoration 4 §2). An underline is SGR 4 — in its `text-decoration-style` as `4:2` double, `4:3` curly (`wavy`), `4:4` dotted, `4:5` dashed — and its color SGR 58; an overline is SGR 53, a line-through SGR 9, `blink` SGR 5. The extensions past ECMA-48's common subset (the styles, the color, the overline) go only to a terminal whose `SgrCapabilities` list them — `App::new` guesses them from the environment, conservatively (`SgrCapabilities::detect`: all for kitty, WezTerm, foot, Ghostty, mintty, VTE 0.60+ and tmux 3.2+ (which passes them on as its outer terminal allows), the underline styles and color for Alacritty and VS Code, the styles for iTerm2 3.4+, none under GNU screen, an older tmux or an unknown terminal; a multiplexer wins over the outer terminal's inherited variables) and `App::with_sgr_capabilities` overrides the guess; a `CrosstermBackend` or `TestBackend` is basic until told — elsewhere an underline is plain `4` and the color and overline are left out. The overline's and the line-through's own color have no SGR: they take the text's. Decorations propagate as §2.1 says — to in-flow descendants' text, not into an atomic inline or an out-of-flow box — but a cell has one line of each kind, so where an inner and an outer box both ask for, say, an underline, the inner one's style and color win (a browser draws both). `spelling-error` / `grammar-error` (Text Decoration 4) are not parsed.
- **The font is drawn as SGR bold and italic** (C9-FONT; CSS Fonts 4 §2.2, §2.4, §3.7). A computed `font-weight` of 600 or more is bold (SGR 1) — `bold`, `bolder`'s steps and the numbers alike, by §2.2's table for the relative keywords; lighter weights draw normal: the terminal's faint (SGR 2) dims the color rather than thinning the strokes, so body text in `300` would read as disabled, and rdom dropped SGR 2 for that reason (T8). `italic` and `oblique` at any angle but `0deg` are italic (SGR 3). The `font` shorthand honours its weight and style and resets `line-height` (to `normal` when it omits it); its size, family, stretch and variant are kept for the CSSOM, and a system font keyword (`menu`, …) sets the family to it and the rest to their initial values. `em` in a pixel length stays 16px whatever `font-size` says (DESIGN "Pixel lengths select").
- **Inline backgrounds only.** Inline borders are not painted.
- **A line box holds its inline blocks in whole rows.** A line grows to the margin box of its tallest inline block (CSS 2.1 §10.8), which sits where its `vertical-align` puts it — on the line's baseline row by default — and paints at its turn in the line as a box (C5G-ATOM-BOX). An inline block's baseline (§10.8.1) is the glyph row of its last in-flow line box, wherever its block flow places it (C9G-ONE-BASELINE) — or its bottom margin edge when it has no line box or clips its overflow. A negative vertical margin on an inline block counts as zero in its line: rows are whole, and an atom pulled above its line box would cover the line before it.
- **No `masonry` / `grid-lanes`, by decision.** CSS Grid 3's masonry layout is a Working Draft whose syntax is still moving (`display: masonry` against `display: grid-lanes`), so rdom does not implement it until the spec settles. Grid Level 1 / 2 is implemented (C7-*): its own departures are the whole-cell tracks of §1 and the entries above.

- **Floats follow CSS 2.1 §9.5 with three simplifications.** A line box's band beside the floats is read on its first row, so a line made taller by an inline block keeps the width of that row; a float met in inline content is placed at its measured height (its content's at its width) before it is laid out, and its exclusion settles to the height layout gives it only after the lines of that run are packed (C8G-FLOAT-MEASURE: the lines after it see the settled height, the run's own lines beside it the measured one — they differ only where a measurement cannot know the laid-out height, as an `auto` scrollbar's row); an intrinsic size (a flex or grid item, an inline block or an absolutely positioned box sized from its content) measures the box's floats as a formatting context of its own — the floats of an enclosing context are not seen, a block child that is no formatting context root is measured on its own (its floats with it, unseen by its later siblings) unless a float is already beside it, and a float's max-content width adds to the in-flow content right after it only.
- **A formatting context root beside floats is placed again once.** CSS 2.1 §9.5 keeps such a box clear of every float's margin box at the height it gets; rdom places it at its pre-layout height and, laid out taller (its text wrapping in the narrower band), places and lays it out again once at that height (C8G-FLOAT-MEASURE). A box whose height changes again in its new place (a wider band) is not chased.
- **`margin-trim` drops one margin of a collapsed-through edge child.** When the first (last) in-flow block child of a block container is empty and its margins collapse through it (CSS 2.1 §8.3.1), CSS Box 4 §3 trims every margin adjoining the trimmed edge; rdom trims that child's start (end) margin and keeps its other one, which still separates the next sibling.

### Positioning

- **A positioned box reads its own `direction`.** CSS 2.1 §9.4.3 / §10.3.7 keep the inline-start inset of an over-constrained box by its containing block's `direction`; rdom reads the box's own, which it inherits from that block unless it sets one. The static position of an `rtl` box with both insets `auto` is still taken from the left.
- **Stacking contexts form from the root, positioned elements and flex / grid items with a numeric `z-index`, `opacity < 1`, a transform, a filter or backdrop filter, a blend mode or `isolation: isolate`, a `clip-path`, layout and paint containment, and a `will-change` naming such a property only.** Paint and hit-test follow CSS 2.1 Appendix E inside each context (negative `z-index` below in-flow content, positioned boxes above it, positive `z-index` on top). In-flow content paints in the Appendix E phases of each paint unit — a context root, a `z-index: auto` positioned box, a float, an atomic box — the block-level boxes' shadows, backgrounds and borders (step 4), the floats (step 5), then the inline content (step 7) (C8G-PAINT-PHASES). Hit-testing tries a context's floats before its in-flow content, so a click on inline content that overflows into a float hits the float, which paints beneath it. A transformable box with a `transform`, `translate`, `rotate` or `scale` other than `none` — even an inert or zero one — is a stacking context and the containing block of its absolutely and fixed positioned descendants (CSS Transforms 1 §2, C15-TRANSLATE). A `filter` or `backdrop-filter` other than `none` is one too, and a containing block likewise (Filter Effects 1 §5, 2 §3; C15-FILTER) — on a box that is not a non-atomic inline box, which has no layer of its own to filter (it paints as its block's lines), so on one the property has no effect. A `mix-blend-mode` other than `normal` and `isolation: isolate` are one too (Compositing 1 §3.2, §5.2; C15-BLEND), and so is a `clip-path` other than `none` — `url()` and `path()` too (CSS Masking 1 §5.1; C15-CLIP-PATH) — on the same boxes. Naming such a property in `will-change` makes the stacking context (and the containing block, where the property would) already, as CSS Will Change 1 §3 asks (C14-CONTAIN).
- **A transform moves a box by whole cells, and does nothing else** (C15-TRANSLATE). CSS Transforms 1 §3 transforms a box's rendering without affecting layout; rdom lays the box out where it is in flow, then moves it and its subtree by the translation — `translate` plus the `transform` list's translate functions, summed exactly (percentages of the `transform-box`: the border box, or the content box for `content-box` / `fill-box`) and rounded once to whole cells, ties to even, within ±65 535 cells — as it moves a relatively positioned box, so paint, hit-testing, `layout_rect()` / `bounding_rect()` and the scroll container's scrollable overflow see the moved box, and the boxes around it do not (§3). There is no untransformed rect to read (a browser's `offsetTop` excludes the transform; rdom has no such API). A pixel length is geometry and rejected (DESIGN, "Pixel lengths select, cells measure"). Rotation, scaling, skews, matrices and perspective are identities, so a translation after `rotate(90deg)` moves by its own offset, unrotated; two `transform` lists whose functions do not pair up interpolate their summed translations and switch their inert functions at the midpoint, where CSS Transforms 2 §12.2 interpolates their matrices. A non-atomic inline box is not transformable (§3) and keeps its place in the line. A translation is layout in rdom, so a running `translate` animation lays out on the frames its cell offset changes — a turning `rotate()` lays out none.
- **A filter maps the colors of the cells its element paints** (C15-FILTER; Filter Effects 1 §5–§6, Filter Effects 2 §3). A cell holds one glyph and two colors, so a filter is a function of a color: the element paints into a layer, and each cell part it painted — the background it filled, the glyph it drew (foreground and underline color), the border it contributed, known by marks its writes leave, not by a color change, so a black box on a black page inverts — has its color mapped through the color-matrix functions in order, in sRGB, rounded once to 8-bit channels; the parts it left keep the backdrop's. A terminal default color (`Color::Reset`) is mapped as the color scheme's canvas color, so it becomes an explicit one. A translucent paint inside blends with the backdrop before the filter maps the result (the spec filters the element's image alone, then composites it). `opacity()` multiplies the group opacity. `drop-shadow()` shades, in whole cells (a pixel offset one cell its way, as `box-shadow`), the cells at its offset from those painted that the element does not paint, in its color through the functions after it; its blur and `blur()` draw nothing, and `url()` references no SVG filter. `backdrop-filter` maps the cells behind the border box (its `border-radius` ignored) before the element paints, as part of the element's group, so `opacity` fades the filtered backdrop too; its backdrop is the backdrop root's image (Filter Effects 2 §3.1) only inside a filter or opacity layer — the cells painted in it — and the whole frame painted so far otherwise.
- **A blend mode blends the colors of the cells its element paints with the backdrop's background** (C15-BLEND; Compositing 1 §3.2, §5.2, §10). A cell holds one glyph, so a glyph cannot mix with the glyph beneath: the element paints into a layer (coverage marks, as a filter's), and each color it painted — the background it filled, its glyph's and border's colors — becomes `B(Cb, Cs)` with `Cb` the backdrop cell's background (the scheme's canvas for a default color), opaque, in sRGB, rounded once; the element's glyph shows, in the blended color, and the backdrop's glyph under a cell it filled is gone, as an opaque fill covers it. The backdrop is the parent stacking context's content (every stacking context is an isolated group, §3.2): in the document's own context every cell, inside another context only the cells that context painted — a cell it painted nothing on is transparent, and the element's color stays. A translucent paint inside the element blends with the backdrop before the blend. `background-blend-mode` is parsed and inert. An isolated group gets a coverage layer only when a member blends, and only on a page where something blends (a document flag).
- **A clip path clips whole cells** (C15-CLIP-PATH; CSS Masking 1 §5, CSS Shapes 1 §3.1). A cell of the element or a descendant paints, and is hit, when its centre is inside the shape laid on the reference box — `inset()` (its `round` radii as elliptical corners), `circle()`, `ellipse()` and `polygon()` (`nonzero` or `evenodd`), each in cells and percentages of the box, or the `<geometry-box>` alone. The geometry is in cells, which are about twice as tall as wide on screen, so a `circle()` is round in cells. `path()` (SVG path data rdom does not draw) and `url()` (no SVG to reference) parse and clip nothing; `xywh()`, `rect()` and `shape()` are not parsed. A pixel length is rejected (geometry); `round`'s `/` form, a `<position>`'s three- and four-value forms, and a `margin-box` whose margin is `auto` (counted 0) are simplifications. The clip applies after the element's filter, so it clips a drop shadow too (§5's order).
- **An outside list marker is drawn beside its item's first line, in whole cells.** CSS Lists 3 §3.5 makes an `outside` marker a box outside the item's principal box; rdom packs the marker text as the item's packer packs text (transform none, letter-spaced, `white-space: pre`) and hangs it on the row of the item's first line box — the item's own, or a block descendant's (`<li><p>Step</p></li>` reads "1. Step"; nested items' markers share the inner item's line) — its end at the item's inline-start border edge, so it sits in the list's `padding-inline-start` (UA: four cells for `ul`, `ol` and `menu` — HTML's 40px is 2.5em at the 16px default font, about five digits; four cells hold "10. " and "iv. "). A marker wider than the padding overflows the list's box into what is beside it, as in a browser, and only the viewport or a clipping ancestor cuts it: a list at column 0 shows "III. " as "II. " (give the list, or an ancestor, a `margin-left` or more padding for wide markers). Departures: a marker hanging on the right (`rtl`, or `marker-side: match-parent` under an `rtl` parent) is written in visual order (`"1. "` → `" .1"`, `"• "` → `" •"`), since rdom lays text out left to right with no bidi reordering; an inside marker keeps its logical order. An outside marker is not in the scrollable overflow (a pointer on it hits its item, as in a browser). When the item has no line box to ride (empty, or a flex child first), the marker makes a line of its own.
- **A block-level `::before` / `::after`'s margins never collapse through its host, and `display: table` on one is not parsed.** CSS 2.1 §12.1 and CSS Pseudo 4 §2 give a pseudo-element the box its `display` and `float` make, and rdom does (C8G-PSEUDO-BOXES, C8G-PSEUDO-ATOMS): a block box of its host's flow, an atomic inline, a float, a flex or grid container of its one anonymous item, or — in a flex or grid container — an item. Two departures: a block-level one is its host's first (last) child for its siblings' margins, which collapse with its own, but its margins do not collapse with its host's (CSS 2.1 §8.3.1 would let a first child's top margin escape the host); and `display: table` (Bootstrap's clearfix) is not parsed until the table formatting context (Phase 13).
- **`quotes: auto` knows a subset of languages.** CSS Generated Content 3 §2.1 leaves `auto`'s marks to the UA, and browsers carry CLDR's delimiters for every language. rdom's table (`rdom_style::auto_quotes`), by the primary subtag of the content language (`lang` / `xml:lang`, HTML §3.2.6.2): `de` `cs` `sk` `lt` `bg` `is` „ “ / ‚ ‘; `fr` « » / « »; `es` `it` `ca` `el` « » / “ ”; `ru` `uk` `be` « » / „ “; `fi` `sv` ” ” / ’ ’; `ja` 「 」 / 『 』; `pl` „ ” / « »; `nb` `no` `nn` « » / ‘ ’; every other language, and none, English “ ” / ‘ ’. Region subtags are ignored (`de-CH` takes German's, where CLDR gives Swiss German « »), and French gets no non-breaking space inside its guillemets — as Chromium and Gecko render `auto`.
- **Counter style symbols are text.** CSS Counter Styles 3 §3.2 lets a `<symbol>` be an `<image>`; rdom takes strings and identifiers only (an image symbol makes its descriptor, or `symbols()`, invalid), and `speak-as` (§3.9) parses and is kept but inert — rdom speaks nothing.
- **The complex predefined counter styles are not defined.** CSS Counter Styles 3 §6's simple styles are all predefined (`rdom_style::counters::predefined_names`), but §7's complex ones — `ethiopic-numeric` and the CJK longhand forms (`japanese-informal` / `-formal`, `korean-hangul-formal` / `-hanja-informal` / `-hanja-formal`, `simp-chinese-informal` / `-formal`, `trad-chinese-informal` / `-formal`) — are not: like any undefined name they format as `decimal`. A representation longer than 60 code points (a `symbolic` or `additive` style's huge value, a long `pad`) is written by the fallback style instead, as §3.1 allows; `pad` never pads past 60.
- **`content` on an element generates nothing.** CSS Generated Content 3 §2 lets a `<content-list>` replace an element's contents (`p { content: "x" }`); Chromium, Gecko and WebKit implement only `<content-replacement>` (an image) on elements, and a string there leaves the children rendered. rdom follows the engines: the value parses, cascades and is computed (`ComputedStyle::content`), the children render, and its `<quote>` items do not move the quote depth. The `contents` keyword is not parsed (no engine ships it), and images are N/A (§1).
- **`::first-line` inherits by value, and takes no `line-height`.** CSS Pseudo-Elements 4 §2.2.1 puts the first line's contents inside a fictional `::first-line` inline box, so an inline descendant inherits each value its own rules leave alone. rdom keeps computed values, not which were inherited: a descendant whose value equals its block's takes the first line's — one that sets the block's own value explicitly (`span { color: inherit }` aside) takes it too. `line-height`, which §2.2.1 lists, is not kept on a `::first-line` rule (the first line does not grow by it). The first line's background paints behind its runs that have none of their own, not as one box around the line's content.
- **`::first-letter` is a styled run unless it floats.** CSS Pseudo-Elements 4 §2.3 makes the first letter an inline box; rdom styles its run of the line (color, background, font weight / style, decorations, `text-transform`, `letter-spacing`, `word-spacing`) without a box of its own, so a non-floated letter's margins, padding, borders, `line-height` and `vertical-align` do not apply — a floated one (a drop cap) is a box with all of them (C10-FIRST). The letter unit (§2.3.2) is leading punctuation, one letter or number, and the punctuation after it, punctuation being ASCII punctuation that is no symbol and the Latin-1, General, CJK and full-width punctuation marks; punctuation followed by white space before any letter leaves no first letter, and a digraph is not one unit. Where both a block and its first block child have a `::first-letter`, the child's alone applies. A floated letter does not count in its block's intrinsic sizes.
- **A highlight overlay applies the values its pseudo-element changes.** CSS Pseudo-Elements 4 §3 paints each highlight pseudo-element (`::selection`, `::highlight()`) with only the properties it sets, the rest showing the layer below; rdom keeps computed values, so a highlight's `color` or decoration counts as set where it differs from the originating element's (its background, not inherited, wherever it paints). Its style is the nearest ancestor's of the text with a style for that highlight — §3.5's highlight inheritance, approximated: an ancestor's highlight values do not merge into a descendant's that sets fewer. Only `color`, `background-color` and the text decoration properties are kept on such a rule (the rest of §3.2 — `text-shadow`, the stroke and fill colors — has no terminal form); generated content and atoms take no highlight (ranges hold DOM positions only). Overlapping highlights paint by `priority`, then registration order, and the selection above them (§5.2, Pseudo 4 §3.5) (C10-HIGHLIGHT). The UA's `::selection` colors are a pair, as §3.4 says: an author `color` or `background-color` there drops the UA's other half (C10G-SELECTION-PAIRED).
- **A `<details>`'s content slot is a box of the box tree, not a node of the document.** HTML §15.5.20 renders a `<details>` with a shadow tree whose second slot, `::details-content`, holds everything but the first `<summary>`; rdom has no shadow tree, so the slot is a box between the element and its content (`box_tree::slot`). Closed, the slot is `content-visibility: hidden` (the UA's rule, CSS Containment 2 §4, C14-CONTAIN): its box stays — its border, padding and background draw, empty — while its content is skipped and keeps its computed styles, as in a browser. A hit on the slot's border or padding targets the `<details>`, its transitions fire their events on the `<details>` with `pseudoElement` `"::details-content"`, and its `scroll` events go nowhere (a browser's fire on its shadow slot, which no document listener sees either). Its transitions run as an element's, geometry included: under `interpolate-size: allow-keywords` a `height: 0` → `auto` transition opens the slot frame by frame (C12-ANIMATABLE), and with `content-visibility` in its `transition` under `allow-discrete` closing animates too — the content shows until the transition ends.
- **A relatively positioned or sticky `::before` / `::after` paints with its flow.** CSS Pseudo 4 §2 positions a pseudo-element as an element, and rdom does (C10-PSEUDO-UNIFY): an absolutely or fixed positioned one is a box placed against its containing block by the elements' placement and stacked by its own `z-index` in its host's stacking context (Appendix E steps 2, 8, 9), hit-tested and counted in its scroll container's overflow; a relative or sticky one is laid out in flow and moved (§9.4.3, CSS Position 3 §3.4). The moved one paints at its in-flow turn — a run of a line after the line's text, a box of its own where its flow paints it — rather than on its context's positioned layer (step 8), so its `z-index` neither orders it nor makes it a stacking context, and its move is not in its scroll container's scrollable overflow. Its percentage `top` / `bottom` resolve against the content box of the block container whose flow holds it when that box's `height` is definite, and are `auto` otherwise (§9.3.2).
- **Inside an `opacity < 1` context, an absolutely positioned descendant whose containing block lies above the context clips to the context's content clip.** CSS 2.1 §11.1.1 would use the clip in effect at the containing block; the difference shows only when an `overflow` box sits between that containing block and the `opacity` element.
- **`text-overflow` has no `fade`.** `fade` and `fade()` (CSS Overflow 4 §3) fade the last characters out over a length — a sub-cell gradient no cell can show; they are not parsed, so the declaration is dropped and a lower one applies. The other values work per line box: whole characters are hidden (a wide one is never split) to fit the marker, whose width is counted in cells (C8-TEXT-OVERFLOW).
- **Line clamping has no fragmentation.** `continue: discard` (CSS Overflow 4 §4.4) hides what follows the clamp point as `collapse` does — rdom has no fragmentation container to discard it into. The legacy form follows the engines: `display: -webkit-box` / `-webkit-inline-box` (kept as such, `ComputedStyle::webkit_box`, and read back as written) with a vertical `-webkit-box-orient` and `max-lines` — from `-webkit-line-clamp` or `line-clamp`, whatever `continue` the later one leaves — is a line-clamp container laid out as a block container (`flow-root` / `inline-block`); without a clamp a `-webkit-box` is a flex container along its `-webkit-box-orient` (a column when vertical; `-webkit-box-direction`, `-webkit-box-pack` / `-align` and `-webkit-box-flex` are not parsed) (C8-LINE-CLAMP, C8G-WEBKIT-CLAMP).
- **`overflow-clip-margin` is whole cells, and takes no viewport-relative length.** Its `<length [0,∞]>` (CSS Overflow 3 §3.2) is rounded onto the cell grid like every length; a length that needs the viewport (`1vw`, a math function holding one) is rejected and the declaration dropped, where CSS would resolve it at computed-value time (C8-OVERFLOW-CLIP).
- **`scroll-padding: auto` is 0, and `scroll-margin` takes no viewport-relative length.** CSS Scroll Snap 1 §4.1 leaves `auto` to the UA ("generally 0px, but … a larger value if appropriate"); rdom has no sticky header to measure and uses 0. `scroll-margin`'s `<length>` is whole cells, either sign, and one relative to the viewport (`1vh`) is rejected, as `overflow-clip-margin`'s is (C8-SCROLL-PADDING).
- **Scroll snapping decides per scroll operation, with a 2-cell proximity.** CSS Scroll Snap 1 leaves the snap-selection details to the UA; rdom's (`runtime::scroll_snap`, C8-SNAP): every wheel tick, arrow or page key, track click and `scrollBy` is a directional scroll of its own — a terminal reports no gesture end to wait for — and rests at the snap position past its start in its direction nearest its destination (under `mandatory` a tick moves a whole item); `scrollTo` / `scrollTop =`, `scrollIntoView`, Home / End and a released thumb drag rest at the position nearest their destination; a `scroll-snap-stop: always` position is not passed by a directional scroll; `proximity` snaps when the chosen position is at most 2 cells from the destination. After a layout that moved the snap position of the box a container rests snapped to, it re-snaps to it (§5.4) — a smooth scroll in flight is retargeted — or, `mandatory`, with the box gone, to the position nearest its offset; a scroll that does not snap (a thumb drag's moves, drag autoscroll, a caret reveal) leaves the container unsnapped until the next snap (C8G-RESNAP). Inside a snap area longer than the snapport every offset at which it covers the snapport is valid (§6.2.3) unless a directional scroll would pass another snap position, the ends of its covering range are snap positions like the aligned ones, and a directional scroll from inside the range that would leave it rests first at the range's end in its direction — rdom's choice, so a page or a tick never skips a tall area's last rows (C9G-SNAP-COVER); rdom does not check §6.2.3's spacing of the neighbouring snap positions for a scroll to a destination, so a position inside such an area is valid even beside a nested snap position (C8G-SNAP-TALL). `block` / `inline` are `y` / `x` (`horizontal-tb`).
- **A flex or grid item's margin is not in its scroll container's scrollable overflow.** CSS Overflow 3 §2.2 counts "the margin areas of grid item and flex item boxes"; rdom counts every in-flow box's border box, and adds the container's end padding past the content (C8G-SCROLLPORT), so an item's end margin in a scrolling flex container is not scrolled to.
- **Sticky containing block is the element's parent's content box**, not the CSS "nearest scroll container" for nested-scroller edge cases.
- **A flex or grid container's baselines are its first and last content rows.** Baseline alignment in flex (`align-items: baseline` / `last baseline`, CSS Box Alignment 3 §9) and an inline block's baseline in its line (CSS 2.1 §10.8.1) read a block container's first and last baselines from its first and last in-flow line boxes — their glyph rows, as layout packs and places them, through block children and anonymous lines alike (C9G-ONE-BASELINE) — but a flex or grid container's (as an item or inside an inline block) as the first and last rows of its content, not from its items' baselines. A box with no line box synthesizes its baseline at its border box's bottom row in flex (Box Alignment §9.1), at its margin box's bottom row as an inline block (CSS 2.1).
- **The static position inside a flex or grid container ignores the alignment properties.** Flexbox §4.1 places an absolutely positioned child's hypothetical box as if it were the sole flex item, so `justify-content: center` would center it; CSS Grid 2 (§10.2 "With a Grid Container as Parent") as if it were the sole grid item in an area that is the container's content box, so its `justify-self` / `align-self` would place it there. rdom uses the content box's start corner (`flex-start`, `start`) in both. In block and inline flow the static position follows CSS 2.1 §10.3.7 / §10.6.4.

### Values

- **Math functions (`calc()`, `min()`, …) accept both `5+5` and `5 + 5` inside the call.** CSS Values L3 requires whitespace around `+`/`-`; rdom's tokenizer doesn't preserve whitespace so the parser accepts either form. `*` and `/` don't need whitespace in CSS either, so those match.
- **Math-function typing: a number is a cell, and a few calculations are refused** (CSS Values 4 §10.9). rdom's length is the unitless cell, so inside a math function a `<number>` joins a `<length>` or a percentage as a length (`calc(50% - 4)`, `min(10, 5ch)`); CSS would reject `<number> + <length>`. Division by a typed value (`calc(10ch / 1ch)`, which Values 4 makes a `<number>`) stays invalid — rdom has one length unit, so the ratio is always the plain division of the numbers. A `<number>` or `<angle>` value is resolved when it is parsed, so a math function in one that holds a viewport unit (`flex-shrink: sign(10vw - 40)`, `atan2(10vw, 10)`) is rejected rather than resolved at computed-value time; a percentage in one is invalid by type unless the property takes percentages (`opacity`: 50% is 0.5). An infinite angle clamps to `MAX_ANGLE_DEGREES` (`f32::MAX` degrees), an infinite length to `±i32::MAX` cells (symmetric, so it negates) before its property's own range.
- **Math functions nest at most 32 levels and build trees at most 256 deep.** CSS Values 4 §10 sets no limit; rdom bounds the parser's recursion (`MAX_CALC_NESTING`: math functions and parentheses) and the expression tree every evaluator walks (`MAX_CALC_DEPTH`: a flat `1 + 1 + …` chain of up to 256 operands). A value past either is invalid at parse time. Math functions take attribute data (`attr()` with `type(<length>)`), so without the bound a hostile attribute could overflow the stack and abort the process. Browsers bound these too.
- **Color functions nest at most 32 levels.** CSS Color 4 / 5 set no limit; rdom bounds the color parser's recursion (`MAX_COLOR_NESTING`: `color-mix()` inside `color-mix()`, a relative color's origin, `light-dark()`'s arms — each color function counts one level). A deeper value is invalid at parse time. Color functions take attribute data (`attr()` with `type(<color>)`), so without the bound a hostile attribute could overflow the stack and abort the process.
- **Percentages on box properties.** `padding` and `margin` percentages (bare or in `calc()`) resolve against the containing block's width on all four sides (CSS Box 3 §3.2 / §4.2); `top` / `right` / `bottom` / `left` / `inset` against the containing block's height or width on the matching axis; `min-*` / `max-*` against the containing block on their axis — against an indefinite height a `min-height` percentage is `0` and a `max-height` percentage is `none` (CSS 2.1 §10.7). A transition between two lengths, percentages or math functions interpolates them as `calc()` mixes (CSS Values 4 §3.4.3), resolved by layout like any `calc()`. A percent `gap` resolves against the container's content size on the gap's axis, and against 0 when that axis is indefinite — rdom takes `height: auto` on a column container as "indefinite" (CSS also treats `height: 50%` under an indefinite parent that way; rdom resolves it against the available height).
- **`border-style: half-block` is rdom-specific.** Not a CSS-spec keyword. Each border cell fills the **quadrants that point inward** toward the bordered element's content — an edge fills a half (`▄ ▀ ▌ ▐`, U+2584/U+2580/U+258C/U+2590), a corner fills a single quadrant (`▗ ▖ ▝ ▘`, U+2596/U+2597/U+259D/U+2598). Pairs with a `background-color`-filled interior to produce a "pill"-style primary-CTA button that reads as ~2 cells tall on a 3-row layout (the half-blocks contribute half-cells of color each, joining the filled interior into a continuous accent region).
- **Half-block borders weld across elements (quadrant union).** When two half-block borders share a cell, the joiner **unions their inward quadrants** and emits the matching block glyph — so a "tab" box whose bottom edge overlaps a panel's top row welds into one tab-panel outline (`▟ █ ▌` at the junction), and any T-junction / cross resolves too. All 16 quadrant combinations have a Unicode block element (`▘▝▖▗ ▀▄▌▐ ▚▞ ▛▜▙▟ █`), so — unlike single-line borders, which have no rounded T-junctions — there are no gaps. This is the half-block analog of `border-collapse` welding and needs no opt-in (two adjacent half-block borders just join).
- **A half-block border keeps the background out of its cells.** `background-clip` works as specified (CSS Backgrounds 3 §3.8; `border-box`, the initial value, paints the background under the border cells too), except that on an element with a half-block side `border-box` acts as `padding-box`: the half-block glyph fills the inward half of its cell, and the outward half must show what lies beneath (the parent's background), or the element's own background would turn the pill silhouette back into a solid rectangle. `padding-box` and `content-box` are unaffected. Switch to another border style to paint the background under the border.
- **`border: rounded`, `border: single` and the one-side `border: top` / `bottom` / `left` / `right` are rdom-specific keywords.** `border: rounded` is `border: solid` plus `border-radius: 1` (rounded corner glyphs `╭╮╰╯`, C4-RADIUS), also beside a width and a color (`border: 1px rounded red`); the radius is written as a side effect of the value, so the `border` shorthand's `!important`, CSS-wide keywords and `removeProperty` do not reach it — write `border-radius` for that. Nor does a later `border`: as on the web, `border` does not set `border-radius`, so `.card { border: rounded } .card.flat { border: solid }` stays rounded, and an author's `dialog { border: 1px solid #ccc }` keeps the UA dialog's radius (its ring is solid with `border-radius: 1`) — write `border-radius: 0` to square the corners (C4-RADIUS; before it, the corner shape was part of the border style and a later `border` squared it). Kept for compatibility; `border-radius` is the CSS way. `single` is a synonym for `solid` wherever a `<line-style>` is accepted; elsewhere (`border-style`, `border-<side>`, `border-<side>-style`) `rounded` is `solid` too, without the radius. `top` / `bottom` / `left` / `right`, on their own in `border`, draw that one side solid and no other (the widths and colors reset as for any `border`). None is a CSS keyword.
- **A bare integer `0`–`255` is a color: an xterm-256 palette index** (`color: 208`, emitted as SGR 38;5;n / 48;5;n). CSS has no such form. The low sixteen indices follow the user's terminal theme, which is the point of using them; a web author would write the hex or `rgb()` value of the palette entry instead.
- **Colors compute to 8-bit sRGB.** A terminal cell takes 24-bit sRGB, so every color function computes to it at parse time: `lab()`, `lch()`, `oklab()`, `oklch()` and `color()` are gamut-mapped into sRGB (CSS Color 4 §13.2, OKLCh chroma reduction) and rounded to bytes, alpha too. CSS keeps their own space and precision, so a wide-gamut color serializes as `rgb()` / `rgba()` here rather than as written, and a transition (interpolated in Oklab, §12.1) starts from the sRGB color — a `none` component does not reach it.
- **The system colors are the terminal's and the UA sheet's colors** (CSS Color 4 §6.2 leaves their values to the platform). `Canvas` and `ButtonFace` are the terminal's default background, `CanvasText` and `FieldText` its default foreground (`reset`); `LinkText` / `VisitedText` / `ActiveText` / `ButtonText` / `AccentColor` / `SelectedItem` the UA accent (dodgerblue), `AccentColorText` / `SelectedItemText` / `MarkText` black, `Mark` yellow, `Highlight` / `HighlightText` the UA selection (`#394B7E` / white), `ButtonBorder` the UA border gray, `Field` the UA field background, `GrayText` the UA muted text — the colors the UA rules use (`color::system`). `VisitedText` equals `LinkText`: there is no history. Inside a color function, where a definite color is needed, the terminal's defaults take the canvas model's colors for the element's color scheme (next entry).
- **The preferred color scheme is the terminal's, and `normal` follows it.** The document's preferred scheme (CSS Color Adjust 1 §2.1) comes from the terminal's background, which the `App` asks for with OSC 11 at startup on Unix (light when black text on it has more contrast than white text); a terminal that does not answer, a non-Unix platform or a headless document is dark (`App::detected_background()` tells an answer from none), and an app sets it with `App::with_color_scheme` / `set_color_scheme` (`CascadeExt::set_color_scheme` without an `App`), which skips the query. The query runs in `App::run` before the first frame and delays startup: up to 200 ms when the terminal answers nothing, up to 800 ms more while a begun reply arrives, and not at all once DA1 answers; keys typed during it are kept and handled after it, and a reply later than the wait is still taken as the answer (rdom reads terminal input itself on Unix, so replies never become keystrokes). A browser renders `color-scheme: normal` light; rdom gives it the terminal's scheme, since the terminal's default colors are the page's. Theme changes are followed on Unix: `App::run` enables DEC mode 2031, and a report (`CSI ? 997 ; 1|2 n`) changes the preferred scheme and restyles the tree; a terminal without the mode never reports, and a scheme the app set is not overridden. On Windows rdom reads input through crossterm's console reader, which delivers no terminal replies: there is no startup query (dark unless the app sets it) and no theme following. `color-scheme` does not change what `Canvas` / `CanvasText` paint — they stay the terminal's own colors — but inside a color function they (and a `currentcolor` that is `reset`) take the canvas model of the element's scheme: black / white when dark, white / black when light.
- **Inside a color function, rdom's own colors take fixed values.** A palette index (`208`) is its xterm color — the low sixteen take xterm's defaults, though a terminal's theme may differ; `reset` is invalid there, because it names the default foreground in one property and the default background in another; and a `currentcolor` whose color is `reset` counts as the canvas model's text color (above). Colors in transitions take the same values, and a transition endpoint that is `reset` interpolates as the canvas model's color for the property's role in the element's scheme — the background for `background-color`, the text for `color` and `border-color` — while a registered custom property's `reset` endpoint, which has no role, changes discretely.
- **`currentcolor` computes to a color in non-inherited properties.** CSS Color 4 §6.4 keeps the keyword as the computed value, so a child that writes `background-color: inherit` resolves it against its own `color`; rdom resolves `background-color` / `border-color` to the element's color at computed-value time, so the child inherits its parent's resolved color. Inherited properties (`caret-color`, `caret-text-color`) keep the keyword and resolve against each element. `revert` / `revert-layer` back to a state whose `currentcolor` is resolved take the `color` cascaded at that state.
- **`reset` is an rdom color keyword** for the terminal's default foreground or background (SGR 39 / 49). CSS has no equivalent keyword: a web author leaves `background-color` at `transparent` (its initial value) to show what is beneath, or writes the system colors `Canvas` / `CanvasText`, which rdom maps to it (below). As a background, `reset` / `Canvas` *paints*: the box's cells are blanked in the terminal's default background (SGR 49), covering what is beneath, as a browser paints `Canvas`; only `transparent` paints nothing.

### Cascade & selectors

- **The flow-relative properties share the physical ones' storage.** CSS Logical 1 §4 keeps `margin-block-start` and `margin-top` as two declarations with one computed value. rdom lays out only `horizontal-tb`, so a block-axis or size property is written into its physical twin's storage when declared (the later declaration wins, as §4 asks) and CSSOM reads either name from it. An inline-axis property (`margin-inline-start`, `border-inline-end-color`, `inset-inline`, the `border-start-end-radius` corners, …) maps by the element's `direction`, so a block keeps it as written, with its later declarations, and the cascade replays them in order with the element's direction; CSSOM reads it from the last declaration that sets it, a shorthand's component included (`margin-inline: 1 2` gives `margin-inline-start` `1`, CSSOM §6.6), in the text its physical twin would serialize. Its `!important` is its own: it marks only the side it maps to for the element (C5G-LOGICAL-IMPORTANT), and `removeProperty` removes that declaration alone.

Supported selector grammar: type, class, ID, attribute, descendant, child (`>`), adjacent sibling (`+`), general sibling (`~`), comma list. Supported pseudo-classes: `:hover`, `:active`, `:focus`, `:focus-within`, `:focus-visible`, `:checked`, `:indeterminate`, `:open`, `:disabled`, `:enabled`, `:valid`, `:invalid`, `:required`, `:optional`, `:read-only`, `:read-write`, `:in-range`, `:out-of-range`, `:default`, `:user-valid`, `:user-invalid`, `:modal`, `:popover-open`, `:first-child`, `:last-child`, `:only-child`, `:empty`, `:root`, `:not(<list>)`, `:is(<list>)`, `:where(<list>)`, `:placeholder-shown`.

- **`:active` follows the primary pointer button only.** The `App` activates the pressed element (Selectors 4 §9.4; `:hover` / `:active` / `:focus-within` match its ancestors too, as on the web) from a left-button press to its release — the release clears it before its own `mouseup` / `click` / `dblclick` run, as in Blink — including a press whose `mousedown` was cancelled (as in Blink); a scrollbar press activates nothing. Browsers also activate a button held down with Space and the labeled control of an active `<label>` (HTML §4.16.3); rdom does neither.
- **`:where(<list>)`** matches like `:is()` (any complex selector in its list) but contributes **zero specificity** (Selectors L4); unlike `:is()`, whose argument list is forgiving, `:where()`'s is not yet — one invalid argument invalidates the selector (Selectors 4 §4.4 makes both forgiving) — the mechanism a component library uses to ship default styles that any author rule overrides.
- **`::placeholder` is the host's `::before` box.** rdom paints an `<input>` / `<textarea>` placeholder as generated content (UA `:placeholder-shown::before { content: attr(placeholder) }`), so `::placeholder` rules (CSS Pseudo-Elements 4 §4.3) are layered onto that box while the control is `:placeholder-shown`; at equal specificity a `::placeholder` rule beats a `::before` one. The UA's muted color is a `::placeholder` rule. Only the `::first-line` properties apply (CSS Pseudo-Elements 4 §2.2.1) — `color`, the background properties, the font properties, the text decoration properties, `opacity`, `text-transform`, `letter-spacing`, `word-spacing`, custom properties — and any other declaration in a `::placeholder` rule is dropped when the rule is built (no warning). Observable difference from the web: an author `input::before` rule also styles the placeholder text, since it is the same box.
- **A pseudo-element takes `:hover` / `:active` only where rdom tracks its pointer state.** Selectors 4 §3.6.3 lets user-action pseudo-classes follow a pseudo-element; rdom accepts them after `::before`, `::after`, `::marker` (the nested `::before::marker` / `::after::marker` too) and `::first-letter` (the generated boxes the hit test can name, `HitTestExt::hit_test_pseudo`) and drops a rule that puts one after any other pseudo-element (`::first-line`, the highlight, scrollbar, `::placeholder`, `::backdrop` and `::details-content` ones) or a logical combination (`::before:not(:hover)`) there. `:focus`, `:focus-visible` and `:focus-within` parse and never match: a pseudo-element is never focused. One pseudo-element is hovered at a time — the innermost under the pointer (a `::first-letter` inside a `::before`'s text, not the `::before`). The state is kept by the `App`, and only while one of its sheets has such a rule (no second hit test per pointer move otherwise); a document cascaded without an `App` has none. A `::first-letter` that a `:hover` rule names exists, unstyled, while the rule does not apply, so it can be hovered (C10-PSEUDO-CHAINS).
- **`::scrollbar`, `::scrollbar-thumb`, `::scrollbar-thumb:vertical` / `:horizontal` are rdom pseudo-elements** modeled on WebKit's `::-webkit-scrollbar` / `::-webkit-scrollbar-thumb` / `:vertical` / `:horizontal`; there is no standard equivalent (CSS Scrollbars 1 has only `scrollbar-color` / `scrollbar-width`). They style the gutter cells that `scrollbar-gutter` reserves; `content` is the cell glyph. As Chromium treats its `::-webkit-scrollbar` pseudo-elements, they apply only while `scrollbar-width` and `scrollbar-color` are both `auto`: once either is set, the bar takes the standard properties alone (C8-SCROLLBAR) — and so drops the keyboard-scroll accent the UA gives `[data-rdom-scroll-focus]::scrollbar-thumb`. `scrollbar-color` is inherited (CSS Scrollbars 1 §2), so setting it on an ancestor — `:root { scrollbar-color: … }` — switches the `::scrollbar` styling off for every scroller below it, the UA's accent included.
- **`:blank` is not implemented, by decision.** Selectors 4 marks it at risk and its meaning has changed between drafts (first `:empty` ignoring whitespace, now an empty form control), so rdom does not add it until it is stable. It is rejected as an unsupported pseudo-class.
- **`unset` is resolved at parse time** from the inherited-property table — an implementation detail with the same observable result as the web; see `DESIGN.md`.
- **Translucent colors composite per cell, one glyph per cell.** A color's alpha (`rgb(… / 50%)`, `#rrggbbaa`, CSS Color 4 §4.2) composites over what lies beneath with the same per-cell rules as `opacity` (next entry): a translucent background blends with the one beneath and tints the glyphs it leaves; translucent text takes the cell from a glyph beneath only at alpha ≥ 0.5, otherwise that glyph stays; a translucent border blends like a glyph. Rules in `DESIGN.md`.
- **`opacity` composites per cell, one glyph per cell.** Group opacity is CSS's (the subtree renders opaque, then blends once), but where a translucent element's glyph overlaps a backdrop glyph only one can show: the element's when `opacity ≥ 0.5` or the backdrop cell is empty, otherwise the backdrop's, tinted toward the element's background. The exception is a layer that repaints the backdrop's own symbol with other state (modifiers, link): the symbol is the same, so there is no contest, and the layer's modifiers and link win at any alpha (only the foreground blends) — this is what lets a translucent `::selection` or highlight overlay restyle text beneath it. `Color::Reset` blends as the canvas of the document's color scheme — white text on black when dark (the default), black on white when light. Rules in `DESIGN.md`.
- **An `App`'s own sheets cascade after the document's `<style>` sheets.** The `App` keeps each connected `<style>` element's sheet live (HTML §4.2.6: re-parsed when its text changes, added / dropped when it is inserted / removed) and orders them in tree order, *before* every sheet registered with the `App` (`App::new`'s, `push_stylesheet`'s) — those play the part of `adoptedStyleSheets`, which CSSOM also orders after the document's sheets. The sheets update at the next frame, not synchronously, as every rdom computed style does. The `media` attribute is the sheet's media list (HTML §4.2.6, `Stylesheet::set_media`): the sheet applies while it matches. `extend_from_style_tags` is the snapshot form for a cascade run without an `App`. All of these sheets share one cascade-layer order (`@layer`, CSS Cascade 5 §6.4), as CSSOM orders a document's sheets together: a layer name is the same layer in every sheet, placed by its first declaration in the order above (`<style>` sheets in tree order, then the `App`'s in push order); anonymous layers are never shared.
- **Registered custom properties check the syntax components rdom has value parsers for.** `@property` / `CSS.registerProperty` (`App::register_property`) accept `*`, `<length>` (cells, units and math functions), `<number>`, `<integer>`, `<percentage>`, `<length-percentage>`, `<angle>`, `<color>`, `<time>`, `<custom-ident>` and literal keywords, with `+` / `#` and `|`; a `<length>` computes to whole cells (a terminal has no sub-cell length; Properties and Values 1 §2.4 makes it absolute), a `<length-percentage>` to its cells and percentage, and a `<length-percentage>` with a percentage inside a math function (`min(50%, 10)`) animates discretely; a syntax naming `<resolution>`, `<image>`, `<url>`, `<transform-function>` or `<transform-list>` is rejected and the registration is invalid. A transition of a registered property reaches the `var()`s of ordinary properties on the element and its descendants (through a restyle of the subtree on each frame the value moves, which reuses the elements' matched rules); another custom property that references it keeps the cascaded (end) value.
- **No at-rule but `@import`, `@layer`, `@scope`, `@property`, `@counter-style`, `@starting-style`, `@keyframes`, `@media`, `@supports` and `@container` is evaluated.** `@import` loads through a host-provided loader (`rdom_css::parse_with_loader`, `App::with_import_loader`); its `supports()` condition and media list condition the imported rules as `@supports` and `@media` would. `@supports` answers for what rdom *parses* (CSS Conditional 3 §6.1): a property it parses and keeps inert — `font-family`, `font-size`, a background image — is supported, as a browser that parses a property reports it, and a pixel geometry value is not (`(width: 10px)` is false, as the declaration would be dropped); `font-tech()` / `font-format()` are false, rdom drawing no fonts; a `<general-enclosed>` is false. Inside a conditional group rule every at-rule follows the condition, as in browsers (CSS Conditional 3 §2): an `@property` registers, and an `@layer` declaration takes its place in the layer order (CSS Cascade 5 §6.4.3), only while the condition holds — re-evaluated when the environment flips it — except under `@container`, whose condition can hold for some element and so always counts; an `@import`'s layer is declared whatever its media list (C14G-CONDITIONAL-SPEC). Every other at-rule (`@charset`, `@font-face`, vendor-prefixed ones) is consumed whole per CSS Syntax 3 §5.4.2 — statement form through `;`, block form through its `{…}` — and reported as `WarningKind::UnsupportedAtRule(name)`; the rules around it are unaffected. `@position-try` is scheduled (§3); `@font-face` and the other font at-rules, `@page`, `@namespace` and `@charset` are not applicable (§1).
- **Media features answer for a terminal** (C14-MEDIA; Media Queries 4 / 5). The viewport is in cells: `width` / `height` (and the deprecated `device-*`) are the terminal's columns and rows, `aspect-ratio` columns over rows, `orientation` `portrait` only when rows outnumber columns; a feature value is a unitless number or `ch` — cells, as in every rdom length — or a pixel length, which a query only selects with (DESIGN "Pixel lengths select, cells measure"; C14G-PX-BREAKPOINTS): `px`, `em` / `rem` (16px, the initial font size, Media Queries 4 §1.3) and the absolute units at CSS's fixed ratios compare at 8px a column for `width` and 16px a row for `height` — the same in `@container` — so `(min-width: 640px)` holds from 80 columns, `(max-width: 15em)` up to 30, and a browser sheet's breakpoints fall across real terminal widths (Tailwind's 640 / 768 / 1024 / 1280px at 80 / 96 / 128 / 160 columns, Bootstrap's 576 / 768 / 992 / 1200px at 72 / 96 / 124 / 150). A value in a unit with no cell measure — `ex`, `cap`, `ic`, `lh` / `rlh`, a viewport unit — leaves its feature *unknown* (neither it nor its `not` matches), and rdom-css warns (`WarningKind::UnmeasuredQueryValue`). Before the document has a viewport — a `CascadeExt` cascade with no `set_viewport` and no layout yet — the size features (`width`, `height`, `aspect-ratio`, `orientation`, `device-*`) are unknown rather than read as 0 × 0 (C14G-CONDITIONAL-SPEC); an `App` always has one. The terminal is `screen` (and `all`); `print` and every other type match nothing; `grid` is 1 (Media Queries 4 §4.4 names a terminal as a grid device); `resolution` is false (no pixel density); `color` is 8 (rdom emits 24-bit color), `color-index` and `monochrome` 0; `update: fast`, `overflow-block` / `-inline: scroll`, `scripting: enabled` (the event handlers are the scripts), `display-mode: standalone` (an app in its own window with no browser chrome), `color-gamut: srgb`, `dynamic-range: standard`, `environment-blending: opaque`. The pointer is a mouse — `hover: hover`, `pointer: fine`, as are `any-hover` / `any-pointer` — because a terminal mouse hits any cell exactly and every target is whole cells: `coarse` would tell a sheet to enlarge targets, which in a terminal costs whole cells for no gain. `prefers-color-scheme` is the document's preferred scheme, the one `light-dark()` reads (from the terminal's background, C3-SCHEME). The preferences (`prefers-reduced-motion`, `-reduced-transparency`, `-reduced-data`, `-contrast`, `forced-colors`, `inverted-colors`) and the pointer and color depth are what the app reports (`App::with_media_preferences`, `CascadeExt::set_media_preferences` without an `App`): no preference, a mouse and 24-bit color until it does — a terminal has no OS setting rdom could read, so `prefers-reduced-motion: reduce` is an app's opt-in (a flag or a config file), and, as in a browser, it turns animations off only through a sheet's `@media`.
- **Container queries are evaluated in layout passes, and `scroll-state()` is not evaluated** (C14-CONTAINER; CSS Conditional 5 §6.4–§6.6). A query container's size is its content box in cells; a size query against an axis the container does not answer (`height` on an `inline-size` container), or against a container not laid out yet, is unknown. rdom's layout is one whole-tree pass, so where a browser styles a container's subtree in the middle of laying it out, rdom lays out, re-cascades the subtree of every queried container whose size moved, and lays out again, up to 8 times per layout (one per level of nested containers; past that the sizes wait for the next layout that runs for another reason, and no frame is asked for) — the result is the browser's, but for a scroll container whose query shows a scrollbar that takes the query back (the gutter comes out of the content box the query reads, CSS Overflow 3 §3.4): such a container is frozen at the first size it returns to, its descendants keeping the styles of their last cascade (C14G-CONTAINER-LOOP). Blink resolves the same cycle by keeping the scrollbar; rdom drops the bar once nothing overflows, so the query result is the narrower box's while the bar is gone. Before a container's first layout its descendants' queries are unknown and its `cq*` units 0, for that first pass only. A style query (`style(--x: y)`) compares a custom property's computed value as text, whitespace collapsed; a standard property in `style()` is unknown, as in the browsers that ship it. `scroll-state()` queries (`stuck`, `snapped`, `scrollable`) parse and are unknown: `container-type: scroll-state` is accepted, and rdom does not track the scroll state they read. A style query reads a container's custom properties as computed, a running transition's value included; a restyle that replays recorded matches (a registered custom property's animation step) matches an element whose rules sit under `@container` again, so its queries follow the animated value (C14G-CONTAINER-FIDELITY). A style change the layout's re-cascade makes transitions from the frame that paints it, and an element's first style — resolved in that re-cascade at the first render — starts no transition. An element both restyled by the frame's cascade and re-cascaded by a container whose size moved in the same frame goes through two style change events, not one: the second takes the first's result as its before-change style. A property the first changed and transitioned still runs from its last painted value (the running transition's current value is the new one's start), but one the first changed *without* a transition — the container's rule is what adds the `transition` — starts from that intermediate, never-painted value, and a property the second change returns to its old value runs a short reversed transition (with its `transitioncancel` / `transitionrun` events) where a browser, resolving the container in the same style change, would start nothing (C14G-DOCS: one before-change style per frame needs the transition hook to compare against the end values of the transitions it started this frame — `TECH_DEBT` `CONTAINER-TRANSITION-1`).
- **`content-visibility: auto` judges relevance by the viewport, the focus and the top layer, after layout** (C14-CONTAIN; CSS Containment 2 §4.4). An `auto` element is relevant while its border box meets the terminal's viewport (no margin around it, and no scroll container's clip is consulted: a box scrolled out of a pane but still inside the terminal stays rendered), while it holds the focus, or while an element in it is in the top layer; a selection or a find-in-page match inside does not keep it. Relevance reads the layout, decided once per `layout_dom` after the container queries settle (HTML's "determine proximity to the viewport", once per rendering update; C14G-CONTAINER-FIDELITY), so a newly rendered `auto` element starts out skipping its contents until the first layout determines its relevance (HTML's initial determination, which fires its event whatever it finds: off-screen rows are never laid out with their contents; C14G-CONTAIN-FIDELITY), and one that becomes relevant or not is re-cascaded and laid out again inside the same `layout_dom` (within the passes C14-CONTAINER's container queries take) — and is not decided again until the next layout; its `contentvisibilityautostatechange` event fires after the frame that painted it. Its skipped contents keep their computed styles (a browser's do too) and are neither laid out, painted nor hit; they stay in the tab order, focusable and copied, as §4 keeps them available to user-agent features, and focusing into them makes the element relevant (C14G-SKIP-WALKS). Its `::before` / `::after` are part of them and are not generated. An animation running in skipped contents keeps its timeline but asks for no frames, as the engines throttle rather than cancel it.
- **Background images parse and draw nothing.** The `background` shorthand takes its full grammar (CSS Backgrounds 3 §3.10): comma-separated layers, each an image (`none`, `url()`, a gradient function), a position with an optional `/ <bg-size>`, a repeat style, an attachment and one or two boxes, in any order, with the color on the final layer only. `background-image` / `-position` / `-size` / `-repeat` / `-attachment` / `-origin` parse their `#` lists and are stored (CSSOM reads them back; omitted sub-values reset to their initial values as on the web), but a cell has no pixels to draw an image into, so they have no effect: only `background-color` paints, clipped by the final layer's `background-clip`. Images, positions and sizes are kept as their CSS text, serialized as CSSOM serializes a specified value (whitespace normalized and keywords, function names and units lowercased — `LINEAR-GRADIENT(RED, BLUE)` reads `linear-gradient(red, blue)`, `left -5% top`; a URL quoted, `url("a.png")`; C4G-SERIALIZE, C5G-CUSTOM-SERIALIZE).
- **Times resolve to whole milliseconds.** `1.5ms` rounds to 2ms: the animation clock ticks in milliseconds and a terminal frame is ~16ms, so sub-millisecond precision has no observable effect. (Percentages keep their fraction — `Size::Percent(f32)` — and round once, onto the cell grid, at layout.)

### DOM API shape

The DOM API is Rust-shaped rather than JS-shaped. The semantics match WHATWG DOM; the surface differs in idiomatic ways.

- **`elements_from_point` returns the DOM ancestor chain of the hit** (root-most first — what the event's `composedPath()` carries), not the web's list of every box stacked under the point. One hit-test walk; a positioned box that overlaps another positioned box reports only the topmost one and its ancestors.

- **A highlight's ranges are all live.** CSS Custom Highlight API 1 lets a `Highlight` hold `StaticRange`s, which no mutation updates, beside live `Range`s; rdom has one `Range` type, and every range a registered highlight holds is kept live (DOM §5.3: text edits, insertions and removals move its boundary points). A `Range` outside the registry — the selection's, one a caller keeps — is a plain value. A text node's data set whole (`set_data`, `set_node_value`) is a replacement of all of it, so the ranges into it collapse to its start, as a browser's do; `edit_text` replaces only its byte range.

- **Handles are arena IDs (`NodeId`), not object references.** A `NodeId` is a slot index plus a generation. Slots are recycled after `drop_subtree` / `remove_child_dropping`, but the generation changes on every recycle, so a handle to a dropped node is rejected by `contains`, `node_or_err`, and every mutation path rather than resolving to the slot's new occupant. There is no garbage collection: a cached id does not keep a node alive (the web's object reference would). Comparing IDs across separate `Dom` instances is meaningless.
- **No `Node.prototype` / `Element.prototype` inheritance.** Behaviors attach via Rust trait impls on `NodeRef` / `NodeMut`.
- **Strong characters are approximated.** HTML §3.2.6.4's `dir=auto` / `<bdi>` directionality (which `:dir()` and the UA's `direction` rules read) takes the first character of Unicode bidirectional class L, R or AL. rdom carries no Bidi_Class table: a character is strong when it is alphabetic (Unicode `Alphabetic`) or LRM / RLM, and right-to-left when it lies in the Hebrew, Arabic, Syriac, Thaana, NKo, Samaritan or Mandaic blocks (U+0590–U+08FF), their presentation forms (U+FB1D–U+FDFF, U+FE70–U+FEFF) or the right-to-left supplementary ranges (U+10800–U+10FFF, U+1E800–U+1EFFF). Alphabetic combining marks in those blocks count as strong where UAX #9 makes them NSM, and a `dir=auto` text control with no strong character is `ltr` (HTML would inherit a non-empty value's `ltr` the same way).
- **Tag and attribute names are case-sensitive.** HTML's ASCII-case-insensitive matching of *names* is not applied — except by the table model (`rdom_core::table`: layout's spans and the column selectors' columns), which recognises `TD` as a `td` (C13G-COLUMN-MATCH). Attribute *values* follow HTML: enumerated keywords (`type`, `method`, `enctype`, `formmethod`, …) match ASCII case-insensitively (§2.3.3, `Dom::input_type_state`, `Dom::is_submit_button`), and attribute selectors treat the values of HTML §4.16.2's list (`type`, `method`, `lang`, `checked`, …) as ASCII case-insensitive, as HTML specifies — the `i` / `s` case flags (Selectors 4 §6.3) override that either way.
- **Snapshots replace live collections.** `child_ids`, `query_selector_all`, attribute iterators, etc. return `Vec<NodeId>` snapshots or iterators — there is no live `NodeList`, `HTMLCollection`, `NamedNodeMap`, or `DOMTokenList`.
- **`classList` is a snapshot `DomTokenList` / `DomTokenListMut`**, plus direct `add_class` / `remove_class` / `toggle_class` / `has_class`; not a live `DOMTokenList`.
- **`getElementById` is arena-wide.** The lookup is index-backed and also finds a *detached* element carrying the id when no connected element does. With duplicate ids the first connected element in document order wins, as on the web. The web only searches the document tree.
- **Boundary-point ordering is a `Dom` method**, `compare_boundary_points(a, b) -> Option<Ordering>` (DOM §5.2's internal algorithm), rather than `Range.compareBoundaryPoints(how, range)`; `None` means the two nodes are in different trees.
- **Attributes are a flat `BTreeMap<String, String>`** exposed as iterator pairs. The `Attr` interface is not implemented.
- **No `Window` vs `Document` split.** The TUI `App` plays both roles.
- **`Dom::root()` is a Fragment, not `<html>`.** `<body>` and `<head>` are not auto-inserted. The Fragment stands for the document and for its root element (C14G-ROOT-ELEMENT): it matches selectors as an element with no name, attributes or classes — `:root`, `*`, `:root > .app`, `:root:has(…)` and the user-action pseudo-classes match it, no type, id, class or attribute selector does — and the cascade styles it before its children, which inherit from it; `computed()` on it reads that style, `rlh` its line height, and its background is the canvas's (CSS Backgrounds 3 §2.11.2: every cell of the viewport, beneath everything). Under a transparent Fragment, an `<html>` child's background propagates, else that `<html>`'s `<body>`'s, else a `<body>` child's — so a parsed HTML document behaves as in a browser — and the propagating element paints none on its own box; any other top-level element paints its own box only. Its box is the initial containing block (CSS 2.1 §10.1: the viewport's size, a block formatting context), so its own box properties — margins, padding, border, sizes, `display`, `position`, `overflow` — do not apply, and it runs no transitions or animations. Its children lay out in block flow in it as a browser lays out `<body>`'s (C13-ROOT-BLOCK) — block boxes whose `auto` height is their content's and whose margins collapse with each other's and their children's (§8.3.1), floats, and inline-level children and text in line boxes (a document has no text children; the Fragment's text paints as `<body>`'s would, with the root's inherited properties). `Dom::document_element()` keeps its DOM meaning — the first element child — and no rendering reads it. A point on the canvas outside every box — inside the viewport the document was last laid out in — hits the root, as a browser's `elementFromPoint` returns `<html>` there (C14-HIT-HTML, implemented by C14G-ROOT-ELEMENT): `hit_test` returns `dom.root()`, a click there dispatches at the root, and the pointer hovering it makes `:root:hover` match; under a blocking modal dialog the inert document takes nothing. An element root (`Dom::with_root_tag`) is the root element, a block in the ICB.
- **`textContent.len()` returns bytes**, not UTF-16 code units.
- **Scroll offsets are also public `TuiExt` fields.** `TuiExt::scroll_x` / `scroll_y` hold `scrollLeft` / `scrollTop`; they are runtime-managed. A direct write (or the `set_scroll` builder setter) repaints on the `App`'s next frame like any scroll offset change — when made through `App::dom_mut`, from an input event's listener, or before the `App` is built. The `App` compares offsets only after such code ran, or after a timer, microtask, rAF callback, injected closure or the tick handler that left evidence of a change (a DOM mutation, a scroll-API or custom-validity write, a `request_redraw`), so an idle tick — or a tick handler that finds nothing to do — walks no tree (`P7G-TICK-TOUCHED-1`); a bare field write from such a callback with none of these waits for the next frame that has one. Such a write is clamped by the next layout, but fires no `scroll` event and does not abort a smooth scroll in flight — the web has no such back door. Write through `TuiAccessorsMut` (`set_scroll_top`, `scroll_to`, …) for the CSSOM View behavior.
- **The IDL `ScrollBehavior` enum is `ScrollBehaviorOption` in Rust**, apart from the `scroll-behavior` property keyword `ScrollBehavior`. `scrollIntoView(alignToTop)` is `scroll_into_view_with(align_to_top.into())` (`From<bool> for ScrollIntoViewOptions`). `ScrollLogicalPosition::Nearest` treats an element exactly as large as the scrollport as fitting (CSSOM View §5.1's strict comparisons leave that case unaligned; browsers align the nearer edge).
- **Smooth scrolling has a fixed duration and curve.** A smooth scroll (`scroll-behavior: smooth` with behavior `auto`, or behavior `smooth`) moves over `SMOOTH_SCROLL_DURATION` (250 ms) with a cubic ease-out at whole-cell positions, starting at the `App`'s next frame and firing `scroll` per step; browsers use a UA-defined, often distance-dependent curve at sub-pixel positions. The `App`'s frames drive it: on a `TuiDom` no `App` runs, a smooth scroll stays pending. Keyboard scrolling steps from the destination of the smooth scroll in flight (browsers accumulate the same way); `scrollBy` adds to the current position, as CSSOM View specifies. The caret reveal of a text control and the listbox / tree cursor reveal are always instant.
- **No `moveBefore()`.** Every move is DOM §4.2.3's removal plus insertion: `append_child` / `insert_before` of an attached node fire the old parent's `childList` removal record, clear focus, hover and selection inside it, take it out of the top layer and, under an `App`, cancel and restart its transitions and animations — as `appendChild` does in a browser. DOM's state-preserving `moveBefore()` (which keeps all of that) is not implemented: it needs a move record that renderers tell apart from a removal, and the focus, top-layer and live-range steps of the "move" algorithm (C12G-MOVE-RECORD).
- **No XML namespaces.** `namespaceURI`, `prefix`, `*NS` method variants are not applicable.
- **No Shadow DOM, no custom elements registry, no `<template>` cloning semantics.**
- **Detached nodes are not garbage-collected.** `remove_child` / `clear_children` / `replace_child` / `replace_children` detach a node but leave it in the arena as a reusable orphan (so it can be reattached). The slot is reclaimed only by `drop_subtree`, or the `remove_child_dropping` / `clear_children_dropping` convenience variants. The web relies on GC to reclaim unreferenced detached nodes; rdom's arena requires **explicit** reclamation, so high-churn callers that won't reattach (e.g. a virtualized list/table re-materializing rows) must drop removed nodes or leak arena slots. (`ARENA-RECLAIM-1`.)

### Events

- **`Event.detail` is one typed enum** (`EventDetail::{Mouse, Key, Input, Transition, Submit, Toggle, …}` with typed accessors such as `as_keyboard()`), not a class hierarchy of `MouseEvent` / `KeyboardEvent` / `InputEvent` interfaces. The payloads match the web's fields; the shape is Rust's.
- **`isTrusted` is inverted as `is_synthetic`.**
- **Listener removal is by handle or `AbortSignal`** (`remove_event_listener(ListenerId)`, or `ListenerOptions::signal`), not function-identity equality on a `removeEventListener(fn)` call.
- **Not implemented:** `composedPath()`, `initEvent()`, `timeStamp`, `passive: true`, `CustomEvent` ≠ `Event` distinction.
- **`keyup` requires kitty-keyboard-protocol terminal support.** rdom-tui enables `KeyboardEnhancementFlags::REPORT_EVENT_TYPES` on startup, but the host terminal has to honor it. Supporting terminals (kitty, foot, WezTerm, alacritty 0.13+, recent xterm) fire `keyup` events for every key release. Non-supporting terminals (legacy xterm, basic VT100, most macOS Terminal.app builds) only ever send `KeyEventKind::Press` — `keyup` listeners on those terminals will never fire. No emulation; if your demo needs cross-terminal key-release behavior, derive it from `keydown` + a timer.
- **No `Window` object — events that target `Window` in HTML target `dom.root()` here.** rdom has no chrome around the document grid; the terminal IS the document. Web-spec events that fire on `Window` (today: `resize`; future candidates that follow the same pattern: hypothetical `beforeunload`, `popstate`, etc.) collapse onto the document root. Authors write `dom.root().add_event_listener("resize", …)` where browsers would use `window.addEventListener`. Bubbling, cancelable flags, and dispatch timing match the HTML spec for the corresponding `Window` event; only the target identity differs.
- **`scroll` events bubble even on non-Document targets.** CSSOM View Module §6: `scroll` on `Document` bubbles, but `scroll` on element targets does NOT bubble. rdom fires every `scroll` event with `bubbles = true` regardless of target — a deliberate divergence that lets consumers install a single listener at `dom.root()` and observe all scroll activity (the showcase's scroll-position indicator works this way; per-scrollable installation would require re-wiring on every subtree swap). Suppress propagation explicitly in handlers if needed.
- **`scroll` events are NOT coalesced per rendering step.** HTML5 says multiple scroll-offset writes between rendering steps collapse to one `scroll` event. rdom fires one `scroll` event per mutation-site call: wheel ticks, scrollbar drag deltas, and each programmatic `set_scroll_top` / `scroll_to` write each fire a separate event. For typical terminal-app patterns (one offset write per crossterm event) this matches HTML behavior; bulk programmatic scrolling (e.g., a loop that mutates `scroll_top` ten times) sees ten events where browsers would deliver one. Pay down with a "dirty scroll" set drained at end-of-event-tick if a consumer hits the difference.
- **Pointer capture is mouse-only.** `set_pointer_capture` / `release_pointer_capture` capture *the mouse* (rdom has no touch or pen pointers, so there is no `pointerId` and no `gotpointercapture` / `lostpointercapture`). While captured, moves and the `mouseup` are dispatched to the capture element as their target, as on the web; capture releases on `mouseup`. The runtime's own text-selection drag takes **no** pointer capture, as in browsers: during it `mousemove` / `mouseup` target what is under the pointer and `click` goes to the common ancestor of the mousedown and mouseup targets; the only runtime default that captures is a scrollbar-thumb drag, on the scrolled element itself. A text-selection drag or scrollbar-thumb drag whose `mouseup` was lost (the button released outside the terminal window) ends on the next button-less move or, on a terminal that reports none, on the next `mousedown`, before that press does anything else — it never extends the old selection or scrolls on. The press also drops the capture the thumb drag took; a capture an author took is not released by a press, only by the `mouseup` or the next button-less move (a browser keeps implicit capture until `pointerup` or `pointercancel`).
- **Drag autoscroll is an explicit opt-in layered on capture.** `dom.set_drag_autoscroll(true)` on a captured drag makes the runtime scroll a scroll container while the pointer is near its edge, re-dispatching the drag at the held pointer each ~50ms tick so the selection follows (DRAG-AUTOSCROLL). The web autoscrolls *implicitly* during native text selection / DnD; rdom's text-selection drag autoscrolls without capture or opt-in (so that case matches) but a custom captured drag must opt in (stricter — avoids autoscrolling a slider that merely captures). **A drag owns one scroll container for its lifetime (sticky):** the container is resolved *once*, the first time the pointer reaches an edge zone, then never re-targeted or disarmed for the rest of the drag. So the captured node (or a text-selection drag's anchor block) scrolling out of view, or the pointer overshooting *past* the container onto a sibling, both keep scrolling that same container — textarea-like, and deliberately unlike a browser, which re-targets the scroll to whatever container is under the cursor and **chains** to the viewport (rdom has no viewport-chaining: the scrollport *is* the surface; it autoscrolls the sticky container and stops at its limit). Edge zone is a cell-grained band (a couple of rows at each edge plus everything beyond) with speed ramping by distance and capped — not the browser's pixel-accelerated curve. Both axes have an edge band; **when the pointer sits in both bands at once, the vertical band wins for that tick** — a browser autoscrolls both axes together.
- **Not implemented:** `dragstart` / `drag` / `drop` / `DataTransfer`, touch events, IME composition events, pointer events beyond mouse.
- **Only a modal `<dialog>` leaves the flow, and its `::backdrop` is unstyled by default.** A modal dialog is in the top layer — centred in the viewport by the UA's `dialog:modal` rules (capped at the viewport less two cells: `6px + 2em` has no pixels to count), painted above every stacking context and outside every clip, the document beneath inert (HTML §6.3, `Dom::is_inert`, shared with the `inert` attribute: nothing outside the dialog takes the focus, a key or the pointer — a dialog with nothing focusable takes the focus itself; Tab cycles inside it, Esc cancels it wherever focus sits, the pointer outside it lands on its `::backdrop`, whose events go to the dialog, and a popover above it from outside it is inert) — as on the web. Two departures: a non-modal `<dialog open>` stays in flow, where HTML's UA sheet positions every dialog absolutely and centres it horizontally; and the UA gives `::backdrop` no tint (HTML's `rgba(0, 0, 0, 0.1)`), so a backdrop paints only when a rule styles it (and, a tint, it keeps the page's glyphs beneath). The dialog itself and a popover take HTML's `background-color: Canvas; color: CanvasText` (the UA's `dialog` and `[popover]` rules): the terminal's default background, painted, so they hide the page under them. A popover's `padding: 0.25em` is under a cell, so none.
- **The `value` / `checked` / `selected` attributes reflect the live state; the defaults live beside them.** On the web those attributes are `defaultValue` / `defaultChecked` / `defaultSelected` and the live state is separate IDL state. rdom mirrors typed text into `value` on every keystroke, writes a slider's position to `value`, flips `checked` on toggle and `selected` on an option pick, and reflects a checkbox's indeterminate flag (HTML's `indeterminate` IDL attribute, which has no content attribute) into an `indeterminate` attribute that activation clears — so attribute selectors, `:checked` (matched on the attribute by rdom-core) and consumers reading the attribute all see the current state — and keeps the defaults in `TuiExt::default_value` / `default_checked` / `default_selected`, captured when the control is seeded or before its first runtime change (a `<select>` captures all its options). A consumer's own `set_attribute` on the live attribute before that first change is therefore captured as the default. `default_value()` / `default_checked()` read the defaults (an `<input>`'s `value` attribute before any capture, and always for the types whose value *is* that attribute: hidden, submit, checkbox, …); `set_default_value()` / `set_default_checked()` write them. There is no dirty-value / dirty-checkedness flag, so a new default never changes the live state — every control behaves as one the user already edited. `<form>` reset restores every control (HTML §4.10.21.5) without firing `input` / `change`. `default_selected()` / `set_default_selected()` do the same for an `<option>`. The `<select>` selectedness setting algorithm (HTML §4.10.7: a single-select dropdown with no option selected selects its first non-disabled option, and keeps only the last of several) writes the `selected` attribute too, capturing the default of each option it flips first, so its pick is never taken for the author's. It runs at mount, after a reset, and after `<option>` / `<optgroup>` insertions and removals; and a consumer adding `selected` to one option of a single-select makes it the only selected one (the last marked wins). Because mutation observers may not mutate the tree, the last two are queued and settled when the `App` next handles an event or draws a frame, not synchronously inside the mutation: code that removes the selected option (or marks another) and reads `select::value` in the same handler sees the unsettled state until then. Without an `App`, `select::seed_all` runs the algorithm over the tree.
- **A text control's value lives in a text-node child, seeded at a boundary.** A text-family `<input>` keeps its live value in a single text child seeded from its `value` attribute, a `<textarea>` in its text child (seeded empty when it has none); the editing pipeline, caret, layout and paint all work on that node. `App::build` seeds the controls present at mount (`input::seed_all`); a control inserted later — or an `<input>` whose `type` becomes a text type — is seeded when the `App` next handles an event or draws a frame, before that frame's layout (`INPUT-SEED-ON-INSERT-1`), and at once when it is focused. A browser's control has its value from creation, so code that inserts `<input value="x">` and reads `input::value` / `TuiAccessors::value` in the same handler, without focusing it, sees `""` until that boundary (the `value` attribute already reads `"x"`). Insertion seeds only a control without a text child: a moved control keeps its live text. Without an `App`, call `input::seed_all` or `input::ensure_seeded`.
- **`toggle` and `beforetoggle` fire synchronously.** HTML queues a `<details>`, `<dialog>` or popover's `toggle` as a task and coalesces two before it runs (an open then a close in one task fire one event); rdom dispatches each `toggle` during the change that causes it, as it does every event (there is no task queue), so each change fires its own. A popover's `ToggleEvent.source` is `ToggleDetail::source`. Because a popover's `toggle` fires inside its show or hide, a `toggle` listener cannot show a popover (`DomError::InvalidState`: HTML refuses a show while the document shows or hides one, and its queued event runs after) — show it from a timer.
- **A popover keeps its place in the Tab order, and its attribute changes settle at the next boundary.** HTML puts a popover's content right after its invoker in sequential focus navigation; rdom's Tab order is tree order. A showing popover whose `popover` attribute changes state is hidden (with its events) when the `App` next handles an event or draws a frame — mutation observers may not change the tree — not inside `setAttribute`; without an `App`, call `popover::hide_popover` yourself. Likewise a removed popover leaves the top layer at once (rdom-core's removing steps), but the popovers nested above it — HTML's removing steps run "hide popover" for it — hide at that boundary, without events.
- **Event dispatch is synchronous**, as on the web; there is no task queue, only the runtime's `queue_microtask` / timers. Listener order follows DOM §2.9 (capture pass, then bubble pass, with the target in both). Microtask checkpoints run after every timer / interval / rAF callback as HTML prescribes; the residual deviation is input: the runtime reads a burst of terminal events per tick and checkpoints once after the burst, not after each input event, and a bare `Dom::dispatch_event` outside an `App` never drains microtasks.

### Selection & editing

- **Selection is single-range only.** Multi-range selection (Ctrl-click in browsers) is not supported.
- **Selection collapses to `None` when an endpoint's node is detached**, rather than relocating to *(parent, index_where_node_was)* per WHATWG DOM removing steps §4.2.5. Affects both `anchor` and `focus` endpoints — if either is inside a detached subtree, the entire selection is cleared. A `Mutation::SelectionChanged { prev, next: None }` fires; consumers wanting "the selection now lives just where the removed thing was" must reconstruct that semantic themselves. Pay down with a proper boundary-point relocation walk when a consumer trips on it.
- **Undo/redo fires `input` only.** `beforeinput` does not fire on history transitions.
- **Undo grouping follows Blink's typing-command model** (the specs leave grouping to the UA; Firefox's differs in detail): a typing run — spaces and word boundaries included — is one step, a Backspace run another, a forward-Delete run another; a switch between them, any selection change the edit did not make (arrow keys, clicks, script, even one that returns the caret to the same spot), paste, cut, undo and redo close the group; there is no idle timer. Typing over a selection that spans text nodes records a compound step that the following keystrokes do not join (Blink would group them).
- **Caret paint composes `caret-color` (cell background) and the rdom-extension `caret-text-color` (glyph foreground).** When either is `auto`, the painter uses the inverse of the cascaded fg/bg at the caret cell — matching browser visual semantics without the legacy SGR-7 REVERSED modifier. There is no `::caret` pseudo-element and the terminal's hardware cursor stays hidden. The painted caret blinks like a browser's (on / off, restarting visible on every caret move, edit, key or click; hidden while the terminal is unfocused), at a rate set by `App::with_caret_blink` rather than the OS setting: `App::new` uses 530 ms, `App::with_backend` starts steady.
- **`caret-shape` draws the painted caret in whole cells** (C12-CARET; CSS UI 4 §6.2.2). rdom hides the hardware cursor and paints its own caret, so the shapes are cell paints: `auto` is `block` — the cell in the caret colors, a terminal's usual text cursor — `underscore` keeps the glyph and underlines the cell in `caret-color` (its color through SGR 58 where the terminal has it, the glyph's color elsewhere, `SgrCapabilities`), and `bar` is a one-eighth block (`▏`) in `caret-color` where the cell shows no glyph (a line's end, a space) and the underscore's underline over a glyph, which a cell cannot show beside a bar. `caret-animation: manual` (§6.2.1) stops the UA blink: the caret stays shown (an unfocused terminal still hides it).
- **`accent-color` tints the glyphs a control draws** (C12-CONTROLS; CSS UI 4 §6.3). A browser fills a checked checkbox or radio, a range track and a progress value with the accent; rdom's controls are glyphs, so the accent is their color: a checked (or indeterminate) checkbox's or a checked radio's whole mark (`[x] `, `(•) ` — its `::before`, over any `color` an author rule gave it), the range slider's track and thumb, the progress bar. An unchecked toggle keeps the text color, and `<meter>` its zone colors, as in browsers.
- **`appearance: none` strips rdom's chrome, which is CSS and paint** (C12-CONTROLS; CSS UI 4 §7.1). A browser stops drawing a native widget; rdom's controls are drawn by the UA sheet and the built-ins' paint, so `none` drops, for the toggles, the buttons and a drop-down `<select>`, the UA origin's `::before` / `::after` rules (the marks, brackets and `▾` — an author `::before` still applies), and the painted bar of `<progress>` / `<meter>` and track of a range slider. A text field's look is ordinary UA CSS (its `Field` background, padding) and stays, as browsers keep the UA's declarations. `base` (CSS Forms' base appearance) and the compat keywords draw as `auto`.
- **`field-sizing: content` replaces the UA's fixed field size** (C12-CONTROLS; CSS UI 4 §7.2). A browser's text field has an intrinsic size from `size` / `cols` / `rows` that `content` swaps for the content's; rdom's UA gives its fields fixed sizes (20 cells, a textarea 20 × 4), so `content` sets a text `<input>`'s or `<textarea>`'s `width` to `max-content` — and a textarea's `height` to `auto`, its rows — wherever no author or inline declaration sets them (an author size still wins, as it does over the intrinsic size in a browser). An empty field shrinks to its padding (its placeholder counts); `<select>`, whose size is its options', is not affected.
- **A resizable box is resized from its corner cell, which shows a `◢` grip** (C12-CONTROLS, C12G-RESIZE-PICKER; CSS UI 4 §4.2). The resizer is one whole cell — the bottom-right cell of the padding box, inside the border — drawn over the content or the end of a scrollbar there (browsers draw a resizer in that corner, over a scrollbar corner when both bars show; a terminal has no sub-cell corner to give it, and a vertical bar alone keeps its full column, its last cell under the grip). A press on it drags the border box with the pointer in whole cells, writing `width` / `height` (only the axes `resize` allows and the move changed; `block` / `inline` as `vertical` / `horizontal`, rdom laying every box out horizontally) into its `style` attribute, its content box never below one cell; browsers also floor it at the size it had. The UA sheet makes `textarea` `resize: both`, as the engines' do.
- **An open drop-down `<select>` lists its options from its own row, in the top layer** (C12-SELECT-TOP-LAYER). A browser's picker is a separate popup (HTML's `::picker(select)`, a popover in the top layer) below or over the field; rdom's is the select's option children overflowing its one in-flow row — the first option on the field's row — rendered in the top layer (`TopLayerKind::Picker`: above every stacking context, outside every `overflow` clip, hit before the page, part of no scroller's overflow) while the select's box stays in flow, so nothing moves. It light-dismisses as an auto popover does (a press and release outside it), but it is no popover: it is neither `:popover-open` nor a close watcher (Esc is the select's own key), and opening it hides no popover. A select not in the document does not open (`showPicker()` throws there).
- **`caret-text-color` is an rdom extension**, not a CSS Working Group property. Browsers have no glyph-color knob for the caret (the underlying cell is the user's font). Terminals paint full cells, so rdom exposes the glyph color separately to let authors tune contrast against `caret-color`.
- **`contenteditable` editing is always plain text.** HTML §6.8.1's true state edits rich content (Enter splits a block, paste keeps markup); rdom's editing pipeline only inserts and deletes text, so Enter inserts `\n` and paste inserts the clipboard's text in both the true and the `plaintext-only` state — the two states behave the same. The attribute itself follows HTML: keywords are ASCII case-insensitive, an invalid value inherits, and a `contenteditable="false"` island inside an editing host is not editable.
- **`user-select`'s "editable element" is an editing host or a text control.** CSS UI 4 §6.1 gives `auto` the used value `contain` on an editable element; rdom applies that to `<textarea>`, text-family `<input>`s and `contenteditable` editing hosts, not to every element inside an editing host (which HTML also calls editable), so a drag inside a `contenteditable` article spans its paragraphs instead of being trapped in the first. `::before` / `::after` are never selectable (their used value is `none` per the spec) because generated content has no DOM position a selection could reach.
- **Copied text is the rendered text with one terminal adjustment.** Copy / cut follow HTML §3.2.7's rendered text collection steps (whitespace collapsed per `white-space`, a line break between blocks, `<br>` → newline, tabs between table cells and newlines between rows by their used `display`, no generated content or list markers). One departure: `<p>` contributes the two required line breaks (a blank line) only when it has a vertical margin — innerText's rule models the browser paragraph margin, and rdom's UA `<p>` has none, so by default paragraphs copy one per line as they display. `user-select: none` text is not copied but still takes part in whitespace collapsing.
- **Disabled form controls have `user-select: none`** in the UA stylesheet, blocking drag-selection inside them. Matches Firefox; Chromium permits selection inside disabled controls.
- **The UA `:disabled` rule also mutes the text color, and a `<fieldset disabled>` matches it.** `:disabled { color: <muted>; user-select: none }` covers every actually disabled element (HTML §4.16.3), and color inherits, so everything inside a disabled fieldset paints muted — its first `<legend>` too, although the controls there stay enabled. Browsers grey only the disabled controls themselves. An author rule on `legend` (or `fieldset:disabled`) restores it.
- **A value-less `<input type=submit>` submits `""`, not a default label.** As the submitter, `<input type=submit name=a>` with no `value` attribute contributes `a=` to `form::collect_with_submitter`. This follows HTML: the entry list takes "the value of the field element" (§4.10.21.4), and a submit input's value (value mode *default*) is its `value` attribute or the empty string; the implementation-defined "Submit" default is only the button's *label* (§4.10.5.1.19). Browsers send that label instead (Chrome `Submit`, Firefox `Submit Query`); rdom paints the `Submit` label but submits the spec's `""`. A value-less `<button>` also contributes `""`, and a reset button never submits.
- **`<input type=image>` is a text-labelled submit button that always submits the coordinate (0, 0).** HTML's Image Button state (§4.10.5.1.20) is a submit button showing an image; rdom has no images, so it paints as a button labelled with its `alt` text — what browsers show when the image is missing — or `Submit` without one. As the submitter it contributes `name.x=0` / `name.y=0` (`x` / `y` without a `name`), never its `value`. HTML's *selected coordinate* is the click point in CSS pixels relative to the image, and (0, 0) for a keyboard or scripted activation; with no image to measure against, rdom uses (0, 0) for every activation, pointer clicks included.
- **Form submission navigates nowhere; the `submit` event carries what it would have used.** The web's submission algorithm builds a request from the form's `action` / `method` / `enctype` / `target` (a submit button's `formaction` / `formmethod` / `formenctype` / `formtarget` overriding them, HTML §4.10.19.6) and navigates. rdom has no navigation: `SubmitDetail` carries those effective values (`Dom::submit_detail`) plus the `no_validate` flag, and the `submit` handler decides what submitting means. `action` and `target` are the raw attribute strings — an empty or relative `action` is not resolved against a document URL, which rdom does not have. Only method `dialog` has a built-in default action (closing the form's ancestor `<dialog>`).
- **`pattern` is a Rust `regex`, not a JavaScript `v`-flag RegExp.** HTML compiles `pattern` as `^(?:pattern)$` with the `v` flag; rdom compiles the same wrapper with the `regex` crate. Ordinary patterns (`[A-Z]{3}`, `\d+`, alternation, `\p{L}`) behave alike, but `\d` / `\w` / `\b` are Unicode-aware in Rust (ASCII in JavaScript), look-around and backreferences do not compile, and the `v` flag's string literals (`\q{…}`) and properties of strings (`\p{RGI_Emoji}`) are not supported (its nested classes and `--` / `&&` set operations are). A pattern that does not compile imposes no constraint, as HTML specifies for an invalid pattern.
- **`type=url` validity is a syntax check.** A URL input suffers `typeMismatch` unless its value, trimmed of ASCII whitespace, is a scheme (`ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )`), `:` and a non-empty remainder without whitespace. The URL Standard's parser (host, port, percent-encoding validation) is not run, so `http://exa%mple` passes where a browser may reject it.
- **Constraint validation on unrendered input types is partial.** The date / time / month / week / color / file input types, which rdom does not render as fields, take their value from the `value` attribute. The date-like ones (`date`, `month`, `week`, `time`, `datetime-local`) parse it, `min` and `max` with HTML §2.3.5's microsyntaxes — an unparsable value is no value — and suffer `rangeUnderflow` / `rangeOverflow` (a `time` whose `max` precedes its `min` is a range across midnight) and so match `:in-range` / `:out-of-range`, but not `stepMismatch` or `badInput`; `color` and `file` suffer only `valueMissing` and `customError`.
- **No validation bubble.** `reportValidity()` and a submission blocked by interactive validation focus the first invalid control whose `invalid` event was not canceled; browsers also show its validation message in a bubble. `validationMessage` is rdom's fixed English (listed on `runtime::builtins::validation::validation_message`), not localized.
- **The button family declares `user-select: none` in the UA stylesheet** (`button`, `input[type=button|submit|reset]`). Browsers also keep a drag from selecting a button's label, but mostly through form-control internals rather than a declared UA rule, so a browser's computed `user-select` on a button is typically `auto` where rdom's is `none`, and an author `user-select: auto` on a button makes its label selectable in rdom. Toggles and `input[type=range]` declare nothing (a click reaches them either way — the text-selection drag takes no pointer capture).
- **A button-family `<input>`'s label is UA `::before` content.** A browser renders the label of `<input type=submit|reset|button>` inside the control (its `value` attribute; without one, an implementation-defined `Submit` / `Reset` for those two types and nothing for `type=button`, HTML §4.10.5.1.19–21). rdom has no form-control internals, so the UA sheet generates it: `input[type=…]::before { content: "[ " attr(value) }`, with `"[ Submit"` / `"[ Reset"` when the attribute is absent, and the box sizes to it (`width: auto`). The label therefore shows in the computed `::before` `content`, follows `value` changes on the next cascade, and an author `::before` rule on these inputs replaces bracket and label together. `<button>` labels itself with its children; its `::before` is only the bracket.

### Runtime & focus

- **Keyboard scrolling does not chain.** Arrow, page and Home / End keys scroll the nearest scroll container of the focus and stop at its ends; a browser chains a keyboard scroll the box cannot take to its scrollable ancestor, as it does the wheel. rdom chains the wheel (and `overscroll-behavior: contain | none` stops it, C8-OVERSCROLL), so a key acts as if every scroll container were `overscroll-behavior: contain`. `overscroll-behavior` has no bounce or glow to suppress in a terminal: `contain` and `none` behave alike.
- **`focus()` flushes style, not layout, and its transitions start at the frame.** HTML's focusing steps update style and layout before deciding whether the target is a focusable area. On a document an `App` runs, `focus()` / `focus_with()` — and `runtime::style_flush::flush_style`, for code about to read `computed()` — cascade the dirty subtrees that hold the element, under the `App`'s sheets (C12-FOCUS-FLUSH), so a handler that shows a panel and focuses its input focuses it. Not flushed, each left to the next frame: layout (the next entry); a whole-tree restyle the `App` has pending — before its first frame, after a sheet-set, color-scheme or terminal-size change — and `<style>` text edited since the last frame; and the `&self` readers (`computed()`, Tab's `is_focusable`), which read the last style update. The transitions and animations a flushed change starts begin at the next frame's transition hook, at its time, against the last frame's before-change style, so two flushes in one handler are one style change where CSS Transitions 1 §3 makes each a style change event. On a document no `App` runs, `focus()` reads the styles the caller's last cascade left. The focus fixup that blurs a focused element once it is hidden runs in each frame that cascades or steps a transition — HTML's rendering update (C7G-FOCUS-FIXUP) — not synchronously.
- **Under an `App`, focusing scrolls at the next layout.** HTML's focusing steps scroll the newly focused element into view at once, flushing layout first; rdom flushes style but not layout from a handler (a layout is a whole-tree pass; C12-FOCUS-FLUSH), so on a document an `App` lays out — focused from a handler, a timer, the keyboard's Tab — the scroll waits for the `App`'s next layout, the one the focus is shown in, and reveals the element where that layout puts it: `scrollTop` read in the same handler is the old one (C8G-FOCUS-SCROLL). On any other document — a bare one, or a second document focused from inside an `App`'s handler — it scrolls at once, against the last layout (C9G-MISC-CORRECTNESS). Focus a pointer moved scrolls nothing, nor does `FocusOptions::new().prevent_scroll(true)` (HTML `preventScroll`).
- **The runtime writes two attributes of its own:** `data-rdom-scroll-focus` on the scroll container the keyboard scrolls (`rdom_tui::runtime::scrollbar::SCROLL_FOCUS_ATTR`, moved before each frame's cascade) and `data-rdom-active` on a tree's active row (`rdom_tui::runtime::builtins::tree::ACTIVE_ATTR`). They are ordinary attributes: author selectors may match them, mutation observers see the writes, and serialization includes them. Browsers keep such state internal.
- **The focus indicator is a typed vocabulary, not a universal outline** (`FOCUS-VOCAB-1`). The web shows focus with an *outline* (a non-destructive ring around the box: the UA's `:focus-visible { outline: auto }`) on **every** focusable element. rdom has `outline` (C12-OUTLINE), but a ring is a cell wide: around a one-row button or field it covers the rows above and below and the column each side — the neighbouring controls and labels — where a browser's ring covers a pixel or two of margin. So the UA does not draw focus with it, and an author `outline: none` removes nothing the UA drew; the UA stylesheet matches the cue to the element kind instead (authors who want the browser look write `:focus-visible { outline: auto }`):
  - **Atomic controls** (`button`, `input`, `textarea`, `select`, `summary`, `a`, `area`) → a `:focus-visible { background }` tint, so a button, toggle or select focused by a mouse click shows none while keyboard focus and text fields do — the browsers' focus-ring rule (heuristics in `rdom_tui::runtime::focus::visible`: a key press without Ctrl / Alt / Super makes focus evident, pointer focus is evident only on a text control or editing host, script focus keeps the previous element's visibility). The pointer judgment is made once the click's events have run, so focus moved during a `click` — by a listener's `focus()`, or by `<label>` activation focusing its control — shows the listeners that run during that click (its own, and the `focus` / `focusin` it causes) the previous `:focus-visible` bit (`Dom::focus_visible`); the bit is settled when the click's events have run, before the next frame styles the new focus. A fill reads as "focused" here because the box *is* the control. `input/textarea/select` keep `!important` only to beat their own field background; the rest are non-important and author-overridable.
  - **Scroll containers** (anything that clips and overflows) → the **scrollbar thumb glyph** of the scroll region the keyboard scrolls turns accent (foreground — a colored handle rather than a filled block); other thumbs are gray. That region is the nearest *overflowing* scroll ancestor of the focus, which no selector can express, so the runtime keeps the attribute `data-rdom-scroll-focus` on it (updated every frame from the previous layout, and only while the focus is evident — `:focus-visible` — like the control tint) and the UA sheet styles `[data-rdom-scroll-focus]::scrollbar-thumb`. Authors may match the attribute too. Zero extra area — it reuses chrome the scroll already owns. Such regions are also keyboard-focusable when they're the focus target (see below) and keyboard-scrollable from wherever the focus is.
  - **Grid / tree / listbox** → the internal cursor (active cell/row) is the cue.
  - **Everything else** (a bare focusable `<div>`/`<table>` with no scrollbar) → **no default cue**; the consumer expresses focus in CSS (e.g. `:focus-visible { outline: auto }` — C12-OUTLINE's ring, which takes no room — or `:focus { border-color }`). A full-area background fill on a large container is destructive and unlike the web's outline, so the substrate does *not* apply one. This replaced the old generic `:focus` tint and its per-element opt-out hacks (`canvas:focus`, `[role=tree]:focus`).
- **`cursor` is the terminal pointer's shape, where the terminal has one** (C12-CURSOR; CSS UI 4 §4.1). The `App` sends the keyword of the element under the pointer as an OSC 22 pointer shape (its CSS name) after each pointer event and frame, only to a terminal known to take CSS names — kitty, foot, WezTerm, Ghostty (`PointerShapes::detect`; a multiplexer or an unknown terminal gets nothing, and `App::with_pointer_shapes` overrides) — and sends `default` back when TUI mode is left, the panic path included. A terminal draws no image pointer, so the `<url>` fallbacks parse and are kept but never shown; no protocol hides the pointer, so `none` shows `default`; and `auto` is the text pointer over a line of selectable inline content or an editable control and `default` elsewhere — a browser shows the text pointer over the glyphs only.
- **No `nav-up` / `nav-down` / `nav-left` / `nav-right`, by decision.** CSS UI 4 marks the directional-focus properties at risk and no browser ships them; focus moves by sequential navigation (Tab / Shift-Tab) and the built-ins' own arrow keys. The properties are unknown and dropped with a warning.
- **`pointer-events` supports `auto` and `none` only.** The SVG-era values (`visiblePainted`, `stroke`, …) have no cell-grid meaning and are invalid. `none` falls through to what is beneath and `auto` descendants are hittable, as on the web.

### ARIA tree (no `<tree>` element on the web)

The web platform has no tree element — trees are built from `role="tree"` / `role="treeitem"` / `role="group"` on `<ul>` / `<li>`. rdom ships that pattern as a native built-in (`runtime::builtins::tree` + UA rules), which means it acts on `role` and `aria-*` where the web platform treats them as accessibility metadata only:

- **`role=tree/treeitem/group` drive built-in styling + behavior.** UA rules key box model, disclosure, and highlight off these roles; the runtime keys keyboard/pointer behavior off them. On the web these are ARIA semantics with no intrinsic styling/behavior.
- **Branch-ness keys on `aria-expanded` *presence*, not child count.** A branch with no loaded children (lazy/async) still renders as a branch with a chevron. `aria-expanded="true|false"` toggles open/closed; absent = leaf.
- **`aria-busy="true"` is the loading-state hook.** App-driven and app-styleable (`[role=treeitem][aria-busy=true] { … }`); rdom ships no built-in busy affordance.
- **The expand/collapse arrow (`▼`/`▶`) is painted into the arrow field**, not generated via `::before`, so it stays aligned with the guide gutter regardless of the row's own pseudo content. Layout is 2 cells per nesting level: `[ancestor trunks][connector ├ /└ ][arrow ▼ /▶  or blank][label]`, the connector aligning under the parent row's arrow column.
- **Tree guide lines (`│ ├ └`) have no web equivalent.** They're emitted as border-glyph contributions and reuse the border joiner. Their color comes from the treeitem's `border-left-color` (`[role=treeitem] { border-color: … }` sets it) even though the item paints no actual CSS border.
- **A `[role=treeitem]`'s background is painted as a full-width row by the guide pass**, not by the normal box fill. On the web a `<li>`'s background covers its own (indented) box and would tint the nested child list; rdom instead fills the entire tree-width row — edge to edge, *including the guide gutter to the left of the indented box* — for exactly the cursor / `aria-selected` row, so the highlight reads as a full row and doesn't bleed onto the open subtree.
- **Active descendant, not roving DOM focus.** The `[role=tree]` container holds focus; the cursor row carries an internal `data-rdom-active` marker and highlights only while the container is focused. The container itself gets no background fill on focus — the focus tint is scoped to atomic controls (`FOCUS-VOCAB-1`), so a tree (or any container) is never flooded; its cue is the active row. A tree is `overflow: visible` by default (like any `<ul>`); a consumer that wants the tree to own its scroll (and thus show the accent thumb cue, `[data-rdom-scroll-focus]::scrollbar-thumb`) sets `overflow-y: auto` + a bounded height on the tree itself — a layout choice, not a UA default.
- **Built-in keys are Arrows + Home/End + Enter/Space only** — no vi keys (`j`/`k`/`g`/`G`); apps add those. Every default action is `preventDefault`-overridable.

### Clipboard

- **System clipboard via `arboard` with OSC 52 fallback** for SSH/tmux. Read/write text only.
- **No `ClipboardItem`, no MIME types, no clipboard permissions model.**
- **Copy serializes selected text preserving visual line breaks** per `white-space: normal` collapse rules.

### Timers & animations

- **Sub-tick precision is the tick rate** (~16ms while animating, ~50ms idle). `setTimeout(fn, 10)` fires at the next tick, not at exactly 10ms. The HTML 4ms nested-timeout minimum clamp does not apply.
- **`calc-size()` is linear in `size`** (C12-ANIMATABLE; CSS Values 5 §10, §11). `calc-size(<basis>, <sum>)` takes a sum linear in `size` (`size * 0.5 + 2`, `size - 10%`) — the form every interpolation produces — and rejects one with `size` inside a math function or multiplied by itself. On `width` / `height` layout sizes a `calc-size()`d box in a second whole-tree pass, from the size its basis laid it out at — none when the sum gives that size back (`calc-size(auto, size)`): the box keeps its basis's layout, so inside it a percentage resolves as against the basis (against an `auto` height, as indefinite; C13G-CALC-SIZE-AUTHORED). On `min-*` / `max-*` the basis is measured where the keyword is (`max-*` takes the intrinsic keywords only; `auto` on `min-*` is the automatic minimum of a box that is no flex or grid item, 0 — a flex item's content-based minimum is not used), and where rdom reads no intrinsic `min-*` / `max-*` keyword (a block's automatic height, a generated box, a grid container's own limits) it reads no `calc-size()` either; on `flex-basis` (`auto`, `content` or an intrinsic basis) it is the sum over the base that keyword gives. `interpolate-size: allow-keywords` animates the keywords of all of them.
- **CSS animations add numbers, lengths and colors; other values replace** (C12-KEYFRAMES; CSS Animations 2 §3.2, Web Animations 1 §5.4.4). Under `animation-composition: add` or `accumulate` a keyframe's value is added to the underlying one for the types rdom's values add — numbers and integers, `<length-percentage>`s (a `calc()` sum when they are not linear), colors (channel by channel in sRGB, clamped) — where `add` and `accumulate` agree; every other value (a shadow list, which `add` would concatenate, a keyword, a track list) replaces, as a discrete value does.
- **A progress timeline's time is the animation's timing scaled to its range** (C12-SCROLL-DRIVEN; Scroll-driven Animations 1, CSS Animations 2 §3.3, Web Animations 2 §4.4). On a scroll or view timeline an `auto` duration shares the attachment range among the iterations and a time-based one keeps its proportions with the delay (`infinite` counts once), the end of the range shows the last keyframe (Web Animations 2's at-the-end rule), and a named range on a scroll timeline — which has none — is the whole timeline; a keyframe selector naming a range (`entry 20%`, §4.4) is placed in the animation's attachment range each frame — its whole active interval, so with several iterations it is a fraction of all of them — and is ignored on a timeline without named ranges. The offsets are whole cells from the scroll origin (`rtl` and the reversed flex axes count from the right or bottom edge), against the last layout's geometry; a timeline that layout moved is stepped again in the same frame (§5).
- **`scroll(root)` follows the root element** (C12-SCROLL-DRIVEN, C14G-ROOT-ELEMENT; Scroll-driven Animations 1 §2.1.1). rdom has no viewport scrolling: the root scroller is an element root when it is a scroll container, and the timeline is inactive otherwise — always under the root fragment, which never scrolls. A pseudo-element's `view()` follows its originating element's box.
- **Transition events at one time go out in creation order** (C12-KEYFRAMES, C12G-MISC; Web Animations 1 §4.4, CSS Transitions 2 §6). A frame's `transition*` and `animation*` events form one stream sorted by the time each happened, transitions before animations at one time and the animations in their composite order (tree order, the element before its pseudo-elements, then `animation-name` order), as the specs sort them. Transitions tied at one time keep the order rdom created them in, where their composite order is tree order, then creation, then property name; the two differ only when one style change starts several transitions.
- **Not implemented:** the Web Animations API (`App::get_animations` lists an element's transitions and CSS animations, with their names, play states and current times, read-only — `Element.getAnimations()` without the `Animation` objects), `requestIdleCallback`, `cancelIdleCallback`, `setImmediate`.
- **A cascade change under a running animation can start a transition** (CSS Transitions 1 §3, C12G-BEFORE-CHANGE). The before- and after-change styles are meant to carry a running CSS animation's value, so changing a longhand an animation drives starts no transition; rdom compares that longhand cascade to cascade, so a class change can start one under the animation. It is masked while the animation applies, but outlives it: `animation: a 1s` on `color` with `transition: color 2s`, changed at 0.5 s, shows the old → new fade for 1.5 s after the animation ends at 1 s, where browsers snap to the new color (C13G-MISC).

### HTML parsing (`rdom-parser`)

`rdom-parser` is a strict template parser, not a browser tree constructor. It follows the HTML tokenizer where that costs nothing (text `<`, RAWTEXT / RCDATA elements, character references, DOCTYPE skipping) and departs where recovery would hide author mistakes:

- **Malformed markup is an error, not repaired.** A missing or mismatched end tag (`<div><p>a</div>`), an unterminated attribute, or EOF inside a tag returns `ParseError` with line / column and a hint; HTML's tree-construction recovery (implied end tags, foster parenting, adoption agency) is not implemented.
- **`<tag/>` self-closes any element**, not just void and foreign elements (HTML ignores the `/` on a non-void HTML element).
- **Attribute names keep their case** (HTML lowercases them); the DOM's attribute lookup is exact-match. Tag names are lowercased as in HTML.
- **Duplicate attributes: the last one wins** (HTML keeps the first), except `class`, whose tokens are unioned into the class list (`<p class="a" class="b">` has both classes; HTML keeps only `a`).
- **Character references** follow HTML §13.2.5.72–80: the WHATWG table, longest-prefix matching, legacy no-`;` names, the attribute-value `=` / alphanumeric caveat, digit-only numeric scanning, the C1 → Windows-1252 remap, U+FFFD for U+0000 / surrogates / out-of-range. No departure; the tokenizer's recoverable parse errors (unknown name, missing semicolon, control / noncharacter code points) are simply not reported, as stated above.
- **`<!DOCTYPE …>` is dropped with no `DocumentType` node** (`Dom` has no such node type). Other `<!…>` and `<?…>` become Comment nodes, as in HTML's bogus-comment state.
- **Whitespace is preserved verbatim** in text nodes, including inter-element whitespace; collapsing happens in `rdom-tui`'s layout per `white-space`, as in the browser's rendering (not parsing) pipeline. The one tokenizer-level exception is honored: a newline right after `<textarea>` is dropped (HTML §13.2.6.4.7). The same rule for `<pre>` / `<listing>` is **not** implemented — `<pre>` keeps a leading newline.
- **`</` followed by a non-letter** ends the current element's children and is then an error, rather than becoming a bogus comment. At the top level any `</…` is an error ("unexpected closing tag at top level") instead of silently truncating the template.

- **The HTML list attributes are presentational hints.** `li` is `display: list-item` and counts through the implicit `list-item` increment (CSS Lists 3 §4.6); `ol` / `ul` / `menu` reset `list-item` (HTML §15.3.8, so a nested bullet list does not advance the enclosing numbering), `ol[reversed]` resets it reversed, and `<ol start>` / `<li value>` / `<ol type>` / `<ul type>` / `<li type>` are presentational hints (`list-style-type` for `type`, its `1 a A i I` compared case-sensitively and its `none disc circle square` ASCII case-insensitively, as HTML's `s` / `i` flags say; `counter-reset: list-item N-1`, `reversed(list-item) N+1` with `reversed`, `counter-set: list-item N`; parsed by HTML's rules for integers), which any author rule beats. As in browsers. The marker is each item's `::marker` (C10-LIST-ITEM).

## 4. Known limitations within shipped features

- **The `block-ellipsis` of a clamped `rtl` line goes on its right.** The `block-ellipsis` goes after the line's content in its visual order — on the right in an `rtl` line too, where CSS Overflow 4 §4.3 puts it at the line's end, the left (C8-LINE-CLAMP).
- **Inline content that overflows its block container is not aligned upward.** `align-content` (CSS Box Alignment 3 §5.1) moves a block container's lines of inline content down into its free space like its block-level content, but a line's rows count from the content box's top (`LineBox::top` is unsigned), so inline content taller than the box under an unsafe `end` / `center` stays at the top, as `safe` would place it; block-level content overflows upward as asked. Gate: `layout_pass::layout_children_aligned`, `tree::shift_lines`.
- **An absolutely positioned box with both insets `auto` on an axis is not self-aligned on it.** CSS Position 3 §4.1 aligns such a box in its static-position rectangle; rdom places it at its static position whatever `justify-self` / `align-self` say (with either inset set, the inset-modified containing block aligns it). Positioned `::before` / `::after` are not self-aligned either. Gate: `positioning::place::self_align`.
- **A starting style inherits from its parent's computed style** (C12-STARTING; CSS Transitions 2 §3). `@starting-style` rules give a newly rendered element — first styled, inserted, or out of `display: none` (itself or under an ancestor) — and a `::before` / `::after` that starts to generate a box the style its transitions start from; the spec has a child inherit from its parent's starting style when the parent has one. rdom computes each starting style (an element's, a `::details-content` box's, a `::before` / `::after`'s) inheriting from the parent's — for a pseudo-element its originating element's — computed style: a child whose only `@starting-style` value is inherited from a parent also starting starts from the parent's after-change value. The other pseudo-elements have no starting style (they do not transition).
- **Only `::before` / `::after` (and `::details-content`) transition and animate.** Their transitions and CSS animations run as an element's, every animatable longhand, geometry included (C12-ANIMATABLE); `::marker` (the nested `::before::marker` / `::after::marker` too), `::first-letter`, `::first-line`, `::backdrop`, `::selection` and the `::scrollbar*` pseudo-elements do not transition or run CSS animations — their styles have no transition slot (`StyleSlot` without a `PresentationStyle`), so a change there applies at once and their `animation-name` runs nothing.

- **iTerm2 may not report mouse motion until the first click.** rdom-tui enables any-motion tracking (`?1003h`) at startup; iTerm2 sometimes drops the mode until it has seen a real button event, at launch and again after every unfocus / refocus, so `:hover` does not follow the pointer until the user clicks once. Every output-side re-arm that was tried (per-byte writes, `?1003l` / `?1003h` toggles at startup, on focus and periodically) was a no-op or made iTerm2 stop accepting mouse capture entirely; the terminal commits to motion tracking only on a real mouse event, which an application cannot inject. Alacritty, Kitty, Ghostty and WezTerm honor the mode immediately. Workaround: click anywhere once after launch or refocus. Not fixable from rdom's side; do not retry output-side fixes.
